# Caliber Learnings

Accumulated patterns and anti-patterns from development sessions.
Auto-managed by [caliber](https://github.com/caliber-ai-org/ai-setup) — do not edit manually.

- **[gotcha]** A sim/flow change (a new stage leg, a new scene transition) breaks `test/e2e/*.spec.ts` specs that assert a fixed `data-shmup-scene` sequence on `#game` — the failure reads as "Expected 'ending', Received 'game'", not as a missing feature. When you add a step to the scene flow, grep the e2e specs for `toHaveAttribute('data-shmup-scene'` and extend the walk (clear → `stageClear` → `waitFrames` → `Enter`) rather than debugging the app.
- **[gotcha]** Adding a row to `UserOptions.display` breaks `test/e2e/display-options.spec.ts`, whose `storedDisplay(page)` assertion uses `toEqual` on the whole saved object — new keys show as unexpected `+` lines. Add the new key with its default to that expectation in the same change.
- **[pattern]** Run `pnpm test:e2e` after `pnpm test` + `pnpm build`: the Vitest suite and the Tizen bundle check pass green while the Playwright specs still fail on scene-flow and saved-options drift. Reproduce a single failure fast with `pnpm exec playwright test --config test/e2e/playwright.config.ts --project=chromium <spec>.spec.ts` (the config path is not the repo root default).
- **[pattern]** For multi-file surgical edits (docs + source + spec in one go), a `python3 - <<'PY'` heredoc that does `assert old in s` before `s.replace(old, new, 1)` is the established approach here — the assert turns a stale anchor into an immediate failure instead of a silent no-op, and the whole set can be followed by one `pnpm exec prettier --write` in the same command.
- **[gotcha]** `grep -rn <CONSTANT> packages/` also matches committed-looking `packages/*/dist/**` build output — stale `dist/` hits make it look like a rename was missed. Scope symbol searches to `packages/*/src` (or `git grep`) when verifying a rename.
- **[convention]** After finishing a plan step, append an `- **As built:**` bullet list to that step's section in `shmup_plan.md` (matching the existing M2-xx / M3-xx entries: what shipped, which files, which decisions were rejected and why, the new Tizen gzip figure) and run `pnpm exec prettier --check shmup_plan.md` — the root research docs are prettier-checked even though Markdown is excluded elsewhere.
- **[gotcha]** Names written into `shmup_plan.md` "As built" notes and TSDoc must be verified against the source before committing — a step's prose invented `GRAZE_RADIUS` (the real export is `GRAZE_MARGIN`) and cited decision `D2` for the internal resolution (it is `D19`). Grep each constant and `D<n>` id you cite.
- **[convention]** When a module gains public API, replace its `**Planned API.**` docblock paragraph with a dated `M<x>-<nn>: {@link …}` line listing the new exports — leaving the "Planned" line behind while the feature ships is the drift to watch for.
- **[pattern]** Stage changes to a 150-file step by explicit path, never `git add -A`: `git status --porcelain | grep '^ M ' | cut -c4- | tr '\n' '\0' | xargs -0 git add --` for tracked edits, then name each new file. Verify with `git diff --cached --name-only | grep -E "node_modules|dist/|\.wgt|coverage|\.turbo|^\.claude|^\.caliber|test-results"` returning nothing.
- **[gotcha]** `CLAUDE.md` at the repo root shows up as untracked (`??`) because Caliber regenerates it — leave it out of a feature commit's staged set unless the commit is specifically a Caliber sync.
- **[convention]** A new dev/test stage (e.g. one reachable via `?stage=<id>`) is preferred over a tenth campaign zone: adding a zone changes the campaign diamond, every route test and every golden replay. Follow the `raster-range` precedent and add an integration test that flies the stage instead.
- **[gotcha]** `pnpm test` / `pnpm build` output is huge — pipe through `grep -E "Test Files|Tests |FAIL"` and `grep -E "Tizen bundle OK|Tasks:|ERROR"` respectively, and give the Bash call a long timeout (the full suite and e2e each run minutes; `pnpm test:e2e` ≈ 3.5 min for 257 specs).
- **[convention]** Review fixes made *after* a step's commit get their own nested bullet under that step's "As built" list (e.g. `- **Review fixes (round 1).** …`), naming the symptom, the call site that was missing, and whether any golden hash moved — do not rewrite the original "As built" prose.
- **[gotcha]** `CLAUDE.md` and `CALIBER_LEARNINGS.md` at the repo root show up as untracked (`??`) because Caliber regenerates them — leave them out of a feature commit's staged set unless the commit is specifically a Caliber sync.
- **[pattern]** Prove a regression test actually regresses: `git stash push -- <changed src files> && pnpm --filter @shmup/core exec vitest run <test paths>; git stash pop` — stashing only the `src/` files leaves the new tests in place, so they must fail. Note `pnpm --filter … exec vitest` exits non-zero (`ERR_PNPM_RECURSIVE_EXEC_FIRST_FAIL`), so chain the `git stash pop` with `;` not `&&`.
- **[pattern]** Iterate on core changes with `pnpm --filter @shmup/core exec vitest run test/<module>/<file>.test.ts` (seconds) before paying for the full root `pnpm test` (minutes) — vitest paths are relative to `packages/core/`, not the repo root.
- **[gotcha]** Long-running verification (`pnpm test`, `pnpm build`, `pnpm test:e2e`) writes nothing to its background-task output file until the command finishes, so `wc -c` on that file stays `0` for minutes and `tail` returns empty — this is not a hang. Use `Monitor` with an until-loop grepping for a completion marker (`Tasks:`, `Test Files`, `ELIFECYCLE`), or check liveness with `pgrep -fc playwright` / `pgrep -c vitest`; never burn turns on `echo`-style no-op polling.
- **[gotcha]** `pnpm format:check && pnpm lint && pnpm typecheck` chained in one Bash call exceeds the 120 s foreground timeout and only the first command's output survives. Run them as separate background tasks, or check just the changed files with `pnpm exec prettier --check <paths>` while the full gates run.
- **[fix]** `git reset` / `git add` failing with `fatal: Unable to create '.git/index.lock': File exists` in this repo is usually Caliber's hook mid-run (it stages `CLAUDE.md` / `CALIBER_LEARNINGS.md`), not a crashed editor. Check `ls -la .git/index.lock`, then `rm -f .git/index.lock` and retry the git command.
- **[pattern]** From the repo root, a single file in any package runs with `npx vitest run --project <core|render-pixi|integration|shell|…> <repo-relative path>` — the project names come from the root `vitest.config.ts` and the paths are repo-relative there (the opposite of the `pnpm --filter … exec vitest` form, whose paths are package-relative). Add `-t "<test name>"` to run one `it`.
- **[pattern]** Re-record ONE golden scenario instead of all of them: `SHMUP_GOLDEN_UPDATE=1 npx vitest run --project integration test/golden/golden.test.ts -t "<scenario name>"`. `pnpm golden:update` re-records all ~78 scenarios (≈ 52 s); the `-t` filter works because each case is an `it.each` named after its `GoldenScenario.name`.
- **[gotcha]** A golden scenario configured with `stageSkip: 'boss'` plays only ~700 ticks, far too short for anything that accumulates (grazes, slowdown load, item drops, meter state) to happen at all — assertions on those counters fail with `expected 0 to be greater than 0`. When the scenario exists to prove a mechanic really runs, drop `stageSkip` and let the bot fly the whole zone (~11 k ticks).
- **[convention]** Adding a pilot to `test/golden/golden.ts` is three edits: widen the `GoldenScenario.bot` union, export the bot factory, and add its branch to `pilotOf` — a missing `pilotOf` branch silently falls through to the 4-way bot and records a misleading golden.
- **[pattern]** To assert a new golden actually exercised a mechanic, thread the `observe` callback of `playGolden(replay, undefined, (w) => …)` and count World state per tick; asserting only on the recorded `expected` block (status/ticks/score) cannot tell a run that used the feature from one that never triggered it.
- **[pattern]** Inspect a recorded golden without decoding it in TS: `python3 -c "import json;d=json.load(open('test/golden/<name>.replay.json'));print(d['expected'])"` — the `expected` block (status, ticks, score, lives, deathTicks, bossDefeated) shows at a glance whether the run was long enough and cleared the boss, and comparing it against a sibling golden's tick count is the quickest sanity check.
