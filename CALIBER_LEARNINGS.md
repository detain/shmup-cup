# Caliber Learnings

Accumulated patterns and anti-patterns from development sessions.
Auto-managed by [caliber](https://github.com/caliber-ai-org/ai-setup) — do not edit manually.

- **[pattern]** Docblock- and comment-only edits are not free: they change a package's lint / typecheck inputs, so after a late round of prose edits inside `packages/*/src`, `apps/*/src` or a test file re-run the gate rather than trusting the earlier green (~30 s lint, ~23 s typecheck with turbo's cache; `pnpm test:e2e` ~3 min+).
- **[pattern]** Adding a host app means sweeping the host lists in the docs, not just adding a page: the ASCII host box and the "new host platform" extension row in `docs/dev/architecture.md`, the build-outputs and root-scripts tables in `docs/dev/build-test-deploy.md`, the profile / per-host tables in `docs/dev/input-profiles.md`, plus `repo-layout.md` and the root README. It also changes what `pnpm test:e2e` builds — update that row of `build-test-deploy.md` when a host joins the `turbo run build:test` list. `grep -n "apps/tizen\b" docs/dev/*.md` finds most of them.
- **[convention]** Player-facing status pages (`docs/client/release-candidate.md`, `preview-build.md`, `outstanding-work.md`) and the plan's status banner must not let "the code is finished" read as "the product shipped". Say plainly what has never run on hardware, never been submitted and is still a placeholder, and link `docs/client/outstanding-work.md`. Sweep with `grep -rn "is verified\|verified on\|has been tested on\|runs on the TV" docs/ README.md CHANGELOG.md` before claiming anything is checked.
- **[convention]** Adding a test file means adding its row to `test/README.md` — one row per file in the table, grouped by `integration/` / `scripts/` / `e2e/` prefix. Nothing enforces it, so it is a review-only rule that is easy to forget. When you later change *how* that test gets its data, the README row and any progress-doc sentence describing it are part of the same edit.
- **[convention]** A host the project has no hardware for (`apps/webos`, Steamworks, the itch.io packer) ships with the "never run on hardware" warning repeated in **three** places — the package README or the script's own docblock, the plan's on-device checklist section, and the client doc — and its packaging CLI (`ares-package`, `tizen package`, butler) is stood in for by a committed validator (`apps/webos/scripts/appinfo.mjs` mirrors `validateConfigXml`). Write the validator, never fake the run.
- **[convention]** The Tizen / webOS bundle **and dist** figures quoted in `CHANGELOG.md` / the progress doc / the docs come from the build's own line, never an estimate or a rounded MB: `pnpm build 2>&1 | grep "bundle OK"` prints both (`app.js … KB` and `N files in dist/ (… KB of 8192.0 KB)`). Quote the printed KB figure verbatim and re-run the build after the last edit.
- **[gotcha]** CI's `test` job runs **only** `pnpm install --frozen-lockfile` then `pnpm test --shard=N/3` — it never runs `pnpm assets` or `pnpm build`. `assets/generated/**` is gitignored (`.gitignore:16`), so any test that reads `assets/generated/atlas/main.json` (or a `dist/`) passes locally off a stale artifact and fails on every clean checkout with `ENOENT`. Same for all three shards: whatever a test needs, it must produce itself.
- **[fix]** A test that needs the atlas imports `buildAtlas()` from `scripts/assets/pipeline.mjs` and reads `manifest` / `pages[0].png.length` in memory — deterministic, ~0.6 s, byte-identical to what `pnpm assets` writes (verified: same frames, same 136,592-byte PNG). That is what `apps/tizen/test/build/tizen-build.test.ts`, `apps/webos/test/build/webos-build.test.ts` and `test/integration/localization.test.ts` already do; copy them rather than `readFileSync`-ing the generated folder. Never "fix" it by skipping when the artifact is absent — in CI the artifact is *never* present, so a guarded version would simply never run.
- **[pattern]** Don't poll `gh run watch` in the background and re-check it — block on the run's own status instead: `until [ "$(gh run view <id> --json status --jq .status)" = "completed" ]; do sleep 30; done; gh run view <id> --json conclusion --jq .conclusion`. Then `gh run view <id> | head -22` lists every job with its duration, which is what you quote (a green CI run here is 13 jobs: format·lint, typecheck, test ×3, build·bench, e2e ×5, e2e-firefox, input probe).
- **[env]** `pnpm bench` must be run **alone on an idle machine** — zone-I's ms/tick budget flakes under CPU contention, so never overlap it with `pnpm test`, `pnpm test:e2e` or a build in another shell. Check `uptime` / `pgrep -fc playwright` before trusting a marginal result.
- **[pattern]** Long-running verification runs in one backgrounded shell that writes its own log and a done-marker; guard any `cat`/`tail` of a not-yet-created log with `2>/dev/null` or the Bash call fails with empty output. A backgrounded task's own `.output` file stays **0 bytes until the process exits** (especially when the command is a pipe into `tail`/`grep`), so never poll it for size. Block on the exit marker instead: `until grep -q "exited with code" <task>.output; do sleep 8; done; cat <task>.output`.
- **[pattern]** After a plan step lands and CI is green, close it on the board with `python3 .claude/plan_board.py` — it re-parses the plan and progress tables, sets the step's status and closes the matching GitHub issue on Projects v2 board #4. Run it after the push, not before, so the board never claims a step that CI later rejects.
- **[correction]** The root `README.md` is for players and newcomers, not a worklog: do **not** describe features as plan steps ("M1-08", "M2-14", "45 of 45 steps"). Describe what the game *is* and what it *does*, and keep plan/step/milestone bookkeeping in `docs/old/shmup_plan.md` and `docs/old/shmup_progress.md`. Feature docs the player reads (the client pages) want names, art and flavour — an enemy or power-up entry is a sprite, its name, and a short in-world blurb — not implementation notes.
- **[pattern]** Art for the docs comes from the committed sources, never hand-drawn or fetched: enemy and weapon sprites live as `*.sprite.json` pixel maps under `assets/source/sprites/` and seeded generators in `scripts/assets/procedural/*.mjs`, and the frame table for any one of them is in the atlas manifest `buildAtlas()` returns. Names and stats for a doc come from the matching `content/enemies/*.enemies.json` / `content/weapons/*.weapons.json` file, so a doc and the game can never disagree.
- **[convention]** `docs/images/**` PNGs are generated, never hand-drawn or hand-edited: `pnpm docs:images` (`scripts/doc-images.mjs`) draws the logo banner, a plate per sprite and a portrait per boss from `assets/source/sprites/**` + `content/`, and `pnpm docs:screens` (`scripts/doc-screenshots.mjs`) captures the real game headlessly. To resize a plate, change the script's scale constant (`SHIP_SCALE`, `ITEM_SCALE`, …) and re-run; `node scripts/doc-images.mjs --check` prints `docs/images is up to date (N images)` and is the fast gate after touching either script or the sprite sources.
- **[env]** `pnpm docs:screens` plays the real game in headless Chromium, so the web test build must exist first: `pnpm turbo run build:test --filter=@shmup/web`. Without it the capture has nothing to load.
- **[gotcha]** GitHub renders Markdown `![](…)` at the PNG's natural size, so a 496×80 boss portrait or a 224² ship plate blows out a table column. In `README.md` and `docs/client/*.md` use raw `<img src="…" alt="…" width="…">` inside the table cell instead — GitHub allows HTML in Markdown and Prettier skips Markdown, so nothing rewrites it.
- **[pattern]** To read a PNG's dimensions, use the repo's own decoder rather than assuming ImageMagick or `file` exist: `node -e "const {decodePng}=require('./scripts/assets/png.mjs'); …"` over the file gives `width`/`height`.
- **[pattern]** `pnpm run lint:root` (`eslint --ignore-pattern "packages/**" --ignore-pattern "apps/**"`) lints only the repo-root tooling and finishes in seconds — pair it with `pnpm exec prettier --check .` after touching `scripts/*.mjs` or root docs instead of paying for the full `pnpm lint`.
- **[convention]** Documentation edits are covered by tests: `integration/e2e-docs.test.ts`, `integration/tooling-config.test.ts`, `integration/cjk-budget.test.ts`, `integration/localization.test.ts`, `integration/module-layout.test.ts` and `integration/tv-engine-floor.test.ts` read the Markdown. After editing `README.md`, `CHANGELOG.md`, `docs/dev/*.md`, `shmup_plan.md`, `shmup_progress.md` or `test/README.md`, re-run that set (`pnpm exec vitest run --project integration`, ~1 min) before assuming the gate is still green.
- **[gotcha]** A python-heredoc replacement that splices a sentence into an existing paragraph leaves an over-100-column line, and Prettier does **not** reflow it (Markdown is excluded) — `prettier --check` still passes. Re-wrap the whole paragraph by hand to ≤100 columns in the same edit; expect two or three passes over the surrounding lines to get the wrap right.
- **[convention]** Adding a test file means adding its row to `test/README.md` — one row per file in the table, grouped by `integration/` / `scripts/` / `e2e/` prefix. Nothing enforces it, so it is a review-only rule that is easy to forget. When you later change *how* that test gets its data, the README row and any `shmup_progress.md` sentence describing it are part of the same edit.
- **[pattern]** Any *derived* figure in the docs (atlas pixels, glyph counts, budget ratios, dist size) must be recomputed from the real artifact before it is quoted — `buildAtlas()`'s manifest gives the page size and the occupied area, the build check's own line gives the dist figure. When a doc's stated *reason* for a decision collapses under correct arithmetic, keep the decision, replace the reason, and fix every copy in the same commit; sweep with a content grep, not by memory. Better still, turn the arithmetic into a test (`test/integration/cjk-budget.test.ts` does).

- **[pattern]** Run the whole gate as one chained command into a log file and grep it — `(pnpm format:check && pnpm lint && pnpm typecheck && pnpm test && pnpm build) > <scratch>/final.log 2>&1; echo "EXIT=$?"; grep -E "Test Files|Tests  |bundle OK|All matched" <scratch>/final.log` — the `EXIT=` line is the only reliable pass/fail signal.

The same sweep applies to a new repo-level script: add it to the `scripts/` line of `repo-layout.md`, `scripts/README.md` and the root README's command block.
- **[convention]** Player-facing prose must not quote engine internals a player cannot see: `x 290`, `48 px from the left edge` and similar simulation coordinates belong in `docs/dev/`, not the bestiary — rewrite them as what the player observes ("it overtakes you and holds on the right"). Behaviour figures a player *can* feel (HP, score, px/tick speeds, wind-up ticks) are fine.
