# Caliber Learnings

Accumulated patterns and anti-patterns from development sessions.
Auto-managed by [caliber](https://github.com/caliber-ai-org/ai-setup) — do not edit manually.

- **[pattern]** A background research/review Agent's full report lives in its raw task output file (`/tmp/claude-*/…/tasks/<task-id>.output`, JSONL of message events), not just in the notification excerpt. Extract the last assistant `text` block with a small `python3` pass over the lines and write it to a scratchpad `.md` before the notification text scrolls away.
- **[fix]** `@typescript-eslint/unbound-method` also fires when you *read or reassign a class's method as a value* — hooking a third-party singleton (`const original = TexturePool.createTexture; pool.createTexture = wrapper`) errors in both the source and the test's fake. The fix that works here: declare a local `interface` whose member is a **property with a function type** (`createTexture: (w: number, …) => unknown`), cast the class through it (`pool as unknown as PooledTextureFactory`), and build the fake from that interface with an arrow property — then reading, comparing and restoring the hook are plain assignments. Have the fake factory return both shapes (`{ pool, handle, calls }`) so the test calls through `handle` and the code under test takes `pool`.
- **[pattern]** A backgrounded Bash call's own output file (`/tmp/claude-*/…/tasks/<id>.output`) can be `Read` directly, and a *foreground* poll over it with a long `timeout` works well: `until grep -qE "Tasks:|ERROR" <file> 2>/dev/null; do sleep 10; done; grep -E "…" <file>`. Pick a marker the run really prints — `"Tests "` for `pnpm test`, `"Tasks:|ERROR"` for `pnpm build`/`pnpm lint` (turbo), `"passed|failed|Error"` for `pnpm test:e2e`.
- **[gotcha]** Do not poll a background Bash task by `until [ -s <its .output file> ]` from *another* background task — the poller's own output file is also empty until it exits, so you end up polling the poller. Poll from a foreground call with a long `timeout`, wait on the real process, or use `Monitor` with `tail -f` on a log you redirected yourself.
- **[pattern]** `pnpm format:check && pnpm lint && pnpm typecheck` chained in one Bash call exceeds the 120 s foreground timeout unless you pass an explicit long `timeout` (e.g. 900000–1800000) and tail/grep each stage. Rough budget: `pnpm format:check` ≈ 30 s, `pnpm lint` ≈ 75–80 s uncached, `pnpm typecheck` ≈ 25 s, `pnpm build` ≈ 47 s (9 turbo tasks), `pnpm test` ≈ 76 s, `pnpm test:e2e` ≈ 3.5 min (259 specs).
- **[fix]** When the chained `pnpm lint … && pnpm typecheck …` call hits the 120 s timeout and returns *empty* stdout, do not re-run the chain — the harness backgrounds it and keeps going. `Read` the returned `backgroundTaskId`'s `.output` file instead; both stages' turbo summaries are there.
- **[gotcha]** A failed `pnpm lint` at the root prints turbo's interleaved tail, which truncates the file and line of each error. Re-run the one failing package (`pnpm --filter @shmup/render-pixi lint | head -40`) to get the real `path:line:col` list before editing.
- **[convention]** A plan step's outcome is recorded as an `- **As built:**` block appended directly after that step's `- **Refs:**` line in `shmup_plan.md`, with one nested bullet per area. Beyond "what was left out and why" and "still manual", the strongest blocks also record **where the implementation deviated from the plan's wording and why** (e.g. "the plan said the built web bundle; the bench needs a purpose-built page because…") and **how a measured number must not be over-read**. Later review fixes get their own nested bullet (`- **Review fixes (round 1).** …`) — do not rewrite the original prose.
- **[convention]** A finished step also updates `shmup_progress.md` in three places at once: the `## Current state — resume point (<date>)` block, the step's own table row (`pending` → `done`, review rounds, new test count, commit shas), and any note whose tense the step invalidated. Re-derive N/M from the file: `grep -c "^| M[0-9]-[0-9]" shmup_progress.md` and `grep "^| M[0-9]-[0-9]" shmup_progress.md | grep -c "| done"`.
- **[convention]** A step that supersedes a claim in an existing doc **edits that claim in place** rather than only appending: a finished review finding gets `~~struck through~~` with "**fixed in M3-0x**", its heading gains `· Addressed by M3‑0x`, the report gains an `> **Update (M3-0x).**` block at the top, and a superseded fact ("the overlay's sixth line") is reworded ("the overlay's last line") so it does not go stale when a later step moves it again.
- **[pattern]** Edit long prose lines in Markdown/plan *and* TypeScript files with a `python3 - <<'PY'` heredoc that asserts the old substring exists before replacing (`assert old in s` / `assert s.count(anchor)==1`) — the anchors are 100-column wrapped sentences that are hard to match exactly with Edit, and the assert turns a silent no-op into a visible failure. Follow Markdown edits with `npx prettier --write <files>` (root Markdown *is* Prettier-checked).
- **[pattern]** To move a whole block inside a long Markdown file, do it in python by `index()`-ing the block's start and the next heading, slicing it out and re-inserting at an asserted anchor — then re-`grep -n` the headings to confirm the new order. Editing around it in place drifts.
- **[pattern]** After renaming any user-visible label or content id, sweep the **whole** tree, sources included: `grep -rn "OLD LABEL" docs/ README.md apps/ packages/ content/ | grep -v node_modules | grep -v "/test/" | grep -v dist/`. Stale names survive in TSDoc `@example` snippets and module docblocks that no test or lint rule checks.
- **[gotcha]** `pnpm test`'s unfiltered tail is only Vitest's per-project "Transform |<project>| transforming modules took Ns" advisory — `tail -25` shows six of those and **no** pass/fail line, which reads as a silent failure. Always `grep -E "Test Files|Tests |FAIL"` instead (current baseline: 662 files / 7,972 tests). Same for `pnpm build` → `grep -iE "app.js|gzip|Tizen bundle OK|ERROR"` (current: `app.js 1490.4 KB (384.1 KB gzip of 512.0 KB)`).
- **[convention]** A new browser-side benchmark or harness under `test/bench/` is **not** part of `pnpm test` (its own Vitest config) — but it still needs `test/tsconfig.json` updated to cover the new files, or `pnpm typecheck` skips them silently.
- **[env]** `pnpm bench` now includes `test/bench/render.perf.ts`, which launches Playwright's Chromium — `pnpm install` downloads **no** browser (Playwright ships no postinstall script and the repo sets no `pnpm.onlyBuiltDependencies`). Run `pnpm exec playwright install --with-deps chromium` once per machine, and make sure any CI job that runs a browser-driven test has that step; `--with-deps` is what brings the system libraries `--use-angle=swiftshader` needs.
- **[gotcha]** A browser-driven test can pass locally purely because an earlier `pnpm test:e2e` populated `~/.cache/ms-playwright`, and then fail on a clean CI runner with `browserType.launch: Executable doesn't exist …`. Prove it the fast way before pushing: run the launch with `PLAYWRIGHT_BROWSERS_PATH=<empty temp dir>` — that reproduces a machine with no browsers without touching your real cache.
- **[pattern]** After landing a step that adds a *new kind* of check (a bench, a spec, a job), check the run it lands in rather than trusting the local gate: `git fetch -q origin && gh run list --branch master --limit 2 --json databaseId,headSha,status,conclusion`, then `gh run view <id> --json jobs --jq '.jobs[]|select(.conclusion!="success" and .conclusion!="skipped")|.name'` and `gh run view <id> --log-failed | grep -iE "error|doesn't exist|timeout"`. The `build · benchmark` job is the one that has no Playwright install by default.
- **[pattern]** Verify a `.github/workflows/ci.yml` edit by parsing it instead of re-reading the diff: `python3 -c "import yaml; d=yaml.safe_load(open('.github/workflows/ci.yml')); [print(s.get('name') or s.get('uses'), '|', s.get('run','')) for s in d['jobs']['<job>']['steps']]"` and print a known-good job (`e2e`) next to it — same parse catches YAML you broke and proves the step order matches the job that already works.
- **[gotcha]** In `@shmup/core`'s SoA pools a kill/cancel only **marks** a slot dead; `pools.flushAll()` in the step's removal phase actually frees it. Any harness or test that tops a pool back up must cancel/clear **before** `game.step()` and refill **after** it — refilling first finds every slot still occupied and spawns nothing (the render bench's bullet pool read 0 until the tick was reordered).
- **[convention]** A benchmark or harness that states a load ("512 bullets, 512 point items, the particle pool full") must assert the **minimum** live count over the measured frames, not the last frame's reading — a pool that sawtooths between half and full otherwise passes a last-frame check while the recorded numbers describe a load that never ran. Any figure quoted in `docs/dev/input-probe-results.md` §11, `shmup_plan.md`'s As-built block and the module docblock has to match what the assertion enforces.
- **[pattern]** When a measured number changes, sweep for **every** place it was written down before committing: `grep -rn "<the figure>" --include=*.md --include=*.ts . | grep -v node_modules`. One bench figure lived in the plan's As-built block, two `docs/dev/*.md` files (one of them a results table header) and a module docblock; nothing in `pnpm test` checks that they agree.
- **[fix]** Do not chain `git fetch && git rebase origin/master && git add …` before staging — the rebase aborts on a dirty working tree (`error: cannot rebase: You have unstaged changes`) and the whole chain returns with nothing done. Compare first (`git log --oneline origin/master -1` vs `git log --oneline -1`); when the remote has not moved, skip the rebase and stage directly.

- **[pattern]** The whole gate fits in a few Bash calls if you pass an explicit long `timeout` (900000–1800000) and tail/grep each stage. Current budget: `pnpm install --frozen-lockfile` ~35 ms, `pnpm format:check` ≈ 30 s, `pnpm lint` ≈ 30–80 s (cached/uncached), `pnpm typecheck` ≈ 17–26 s, `pnpm test` ≈ 75 s, `pnpm build` ≈ 18–47 s (0.1 s on FULL TURBO), `pnpm test:e2e` ≈ 3.5 min (259 specs), `pnpm bench` ≈ 3 min (18 tests; the render bench alone ≈ 2 min).
