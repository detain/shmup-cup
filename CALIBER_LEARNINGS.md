# Caliber Learnings

Accumulated patterns and anti-patterns from development sessions.
Auto-managed by [caliber](https://github.com/caliber-ai-org/ai-setup) — do not edit manually.

- **[pattern]** Edit long prose lines in Markdown/README/plan *and* TypeScript files with a `python3 - <<'PY'` heredoc that asserts the old substring exists before replacing (`assert old in s` / `assert s.count(anchor)==1`) — the anchors are 100-column wrapped sentences that are hard to match exactly with Edit, and the assert turns a silent no-op into a visible failure. Wrap it in a small `patch(path, [(old, new), …])` helper when touching several files in one call. Follow Markdown edits with `npx prettier --write <files>` (root Markdown *is* Prettier-checked by `pnpm format:check`).
- **[pattern]** To move a whole block inside a long Markdown file (e.g. re-ordering a README section), do it in python by `index()`-ing the block's start and the next heading, slicing it out and re-inserting it at an asserted anchor — then re-`grep -n` the three headings to confirm the new order. Editing around it in place drifts.
- **[pattern]** After renaming any user-visible label or content id, sweep the **whole** tree, sources included: `grep -rn "OLD LABEL" docs/ README.md apps/ packages/ content/ | grep -v node_modules | grep -v "/test/" | grep -v dist/`. Stale names survive in TSDoc `@example` snippets and module docblocks (`apps/tizen/src/boot/index.ts`, `packages/core/src/ui/index.ts`, `packages/input-web/src/rebind/index.ts`) that no test or lint rule checks.
- **[gotcha]** Editing TSDoc inside `packages/*/src` or `apps/*/src` is not a "docs-only" change: Prettier checks `.ts`, and the Tizen bundle budget is re-measured — re-run the full `format:check → lint → typecheck → test → build → test:e2e` gate after such an edit, not just `format:check`.
- **[fix]** Do not chain `git fetch && git rebase origin/master && git add …` before staging — the rebase aborts on a dirty working tree and the whole chain returns empty output with nothing done. Compare first (`git log --oneline origin/master -1` vs `git log --oneline -1`); when the remote has not moved, skip the rebase and stage directly.
- **[pattern]** Verify a new doc heading's anchor before linking to it: one chained `grep -n "^## <Heading>" <file> && grep -n "^### <Heading>" <file> && …` call over every file you added a cross-link to. Nothing in `pnpm test` checks doc links, and GitHub-slugged anchors with backticks/em-dashes are easy to get wrong.
- **[gotcha]** `pnpm test`'s unfiltered tail is only Vitest's per-project "Transform |<project>| transforming modules took Ns" advisory — `tail -25` shows six of those and **no** pass/fail line, which reads as a silent failure. Always `grep -E "Test Files|Tests |FAIL"` instead (current baseline: 659 files / 7,958 tests). Same for `pnpm build` → `grep -iE "app.js|gzip|Tizen bundle OK|ERROR"`.
- **[pattern]** The whole gate fits in a few Bash calls if you pass an explicit long `timeout` (900000–1800000) and tail/grep each stage. Current budget: `pnpm install --frozen-lockfile` ~35 ms, `pnpm format:check` ≈ 30 s, `pnpm lint` ≈ 80 s uncached, `pnpm typecheck` ≈ 26 s, `pnpm test` ≈ 75 s, `pnpm build` ≈ 18–47 s, `pnpm test:e2e` ≈ 3.5 min (259 specs). Without an explicit timeout the chain dies at the 120 s default and only the first command's output survives.
- **[gotcha]** `pnpm install --frozen-lockfile` is near-instant here (~35 ms, "resolution step is skipped") — running it before a gate costs nothing and rules out a stale link, so keep it at the head of the verification chain.
- **[pattern]** Re-check the Tizen size budgets without a rebuild: `node apps/tizen/scripts/check-bundle.mjs` (runs fine from the repo root, no `cd`) reads the existing `apps/tizen/dist/` and prints `Tizen bundle OK: app.js … KB (… gzip of 512.0 KB)`. Quote that gzip figure in CHANGELOG / progress rather than guessing.
- **[gotcha]** A bucket-picking helper written as a `<` chain silently mis-classifies `NaN` (every comparison is false, so it falls through to the overflow bucket). Write the chain negated — `if (!(ms >= edge)) return i;` — so a `NaN` lands in bucket 0, and check the `@example` in its docblock actually matches the edges.
- **[gotcha]** Test *helpers* are linted with the same type-aware rules as sources: a harness object literal whose shorthand method is later destructured trips `@typescript-eslint/unbound-method` — declare it as a property with an arrow instead; and a ternary used as a statement (`cond ? a.push(x) : a.push(y)`) trips `@typescript-eslint/no-unused-expressions` — write `a.push(cond ? x : y)`.
- **[gotcha]** `apps/electron`'s `test/main/main.test.ts` (the F11 fullscreen / Ctrl+= scale `vi.waitFor` assertion) is flaky under the full `pnpm test` load — it passes on its own (`pnpm --filter @shmup/electron exec vitest run test/main/main.test.ts`, ~2 s) and on a second full run. Re-run the single file, then re-run `pnpm test`; only treat it as a real break if it fails twice.
- **[pattern]** For a long run whose result you need in full, redirect to a log file in the session scratchpad and background the Bash call, then pull failure detail out with `grep -a -A30 "Failed Tests" <log>`. The `-a` matters: Vitest's log has escape bytes and plain `grep` calls it a binary file.
- **[fix]** Wrapping a wait in a *background Bash* task (`until grep -q EXIT= log; do sleep 5; done`) does not help — that task's own output file is also empty until it exits, so you end up polling the poller. Use `Monitor` with `tail -f -n 0 "$LOG" | grep -E --line-buffered "<done marker>|✘|failed|Error:"` and a generous `timeout_ms`, or wait on the real process, or poll from a foreground call with a long `timeout`.
- **[pattern]** A background research/review Agent's full report lives in its raw task output file (`/tmp/claude-*/…/tasks/<task-id>.output`, JSONL of message events), not just in the notification excerpt. Extract the last assistant `text` block with a small `python3` pass over the lines and write it to a scratchpad `.md` before the notification text scrolls away.
- **[fix]** `@typescript-eslint/unbound-method` also fires when you *read or reassign a class's method as a value* — hooking a third-party singleton (`const original = TexturePool.createTexture; pool.createTexture = wrapper`) errors in both the source and the test's fake. The fix that works here: declare a local `interface` whose member is a **property with a function type** (`createTexture: (w: number, …) => unknown`), cast the class through it (`pool as unknown as PooledTextureFactory`), and build the fake from that interface with an arrow property — then reading, comparing and restoring the hook are plain assignments. Have the fake factory return both shapes (`{ pool, handle, calls }`) so the test calls through `handle` and the code under test takes `pool`.
- **[pattern]** A backgrounded Bash call's own output file (`/tmp/claude-*/…/tasks/<id>.output`) can be `Read` directly, and a *foreground* poll over it with a long `timeout` works well: `until grep -qE "Tasks:|ERROR" <file> 2>/dev/null; do sleep 10; done; grep -E "…" <file>`. Pick a marker the run really prints — `"Tests "` for `pnpm test`, `"Tasks:|ERROR"` for `pnpm build`/`pnpm lint` (turbo), `"passed|failed|Error"` for `pnpm test:e2e`.
- **[gotcha]** Do not poll a background Bash task by `until [ -s <its .output file> ]` from *another* background task — the poller's own output file is also empty until it exits, so you end up polling the poller. Poll from a foreground call with a long `timeout`, wait on the real process, or use `Monitor` with `tail -f` on a log you redirected yourself.
- **[pattern]** `pnpm format:check && pnpm lint && pnpm typecheck` chained in one Bash call exceeds the 120 s foreground timeout unless you pass an explicit long `timeout` (e.g. 900000–1800000) and tail/grep each stage. Rough budget: `pnpm format:check` ≈ 30 s, `pnpm lint` ≈ 75–80 s uncached, `pnpm typecheck` ≈ 25 s, `pnpm build` ≈ 47 s (9 turbo tasks), `pnpm test` ≈ 76 s, `pnpm test:e2e` ≈ 3.5 min (259 specs).
- **[fix]** When the chained `pnpm lint … && pnpm typecheck …` call hits the 120 s timeout and returns *empty* stdout, do not re-run the chain — the harness backgrounds it and keeps going. `Read` the returned `backgroundTaskId`'s `.output` file instead; both stages' turbo summaries are there.
- **[gotcha]** A failed `pnpm lint` at the root prints turbo's interleaved tail, which truncates the file and line of each error. Re-run the one failing package (`pnpm --filter @shmup/render-pixi lint | head -40`) to get the real `path:line:col` list before editing.
- **[convention]** A plan step's outcome is recorded as an `- **As built:**` block appended directly after that step's `- **Refs:**` line in `shmup_plan.md`, with one nested bullet per area. Beyond "what was left out and why" and "still manual", the strongest blocks also record **where the implementation deviated from the plan's wording and why** (e.g. "the plan said the built web bundle; the bench needs a purpose-built page because…") and **how a measured number must not be over-read**. Later review fixes get their own nested bullet (`- **Review fixes (round 1).** …`) — do not rewrite the original prose.
- **[convention]** A finished step also updates `shmup_progress.md` in three places at once: the `## Current state — resume point (<date>)` block, the step's own table row (`pending` → `done`, review rounds, new test count, commit shas), and any note whose tense the step invalidated. Re-derive N/M from the file: `grep -c "^| M[0-9]-[0-9]" shmup_progress.md` and `grep "^| M[0-9]-[0-9]" shmup_progress.md | grep -c "| done"`.
- **[convention]** A step that supersedes a claim in an existing doc **edits that claim in place** rather than only appending: a finished review finding gets `~~struck through~~` with "**fixed in M3-0x**", its heading gains `· Addressed by M3‑0x`, the report gains an `> **Update (M3-0x).**` block at the top, and a superseded fact ("the overlay's sixth line") is reworded ("the overlay's last line") so it does not go stale when a later step moves it again.
