Accumulated patterns and anti-patterns from development sessions.
Auto-managed by [caliber](https://github.com/caliber-ai-org/ai-setup) — do not edit manually.

- **[convention]** Test counts quoted in `shmup_progress.md` must come from the run that actually passed — write the row with a placeholder and fill it from the green run; a guess is always wrong. Current baselines (2026-09-16, after M3-02e): root suite **683 files / 8,169 tests**, e2e **277 specs** (chromium + the Firefox determinism spec), bench 21 tests, shell project 63 files / 457 tests, `tools/input-probe` **20 files / 533 tests**.
- **[convention]** The Tizen bundle figure quoted in `CHANGELOG.md` / `shmup_progress.md` comes from the build's own line, never an estimate: `pnpm build 2>&1 | grep "Tizen bundle OK"` → `app.js 1500.9 KB (386.9 KB gzip of 512.0 KB)`. Re-run the build after the last edit and quote that run.
- **[pattern]** The whole gate fits in a few Bash calls if you pass an explicit long `timeout` (900000–1800000) and grep each stage; without one the chain dies at the 120 s default and only the first command's output survives. Current budget: `pnpm format:check` ≈ 30 s, `pnpm lint` ≈ 24–79 s, `pnpm typecheck` ≈ 19–35 s, `pnpm test` ≈ 78 s–10 min under load, `pnpm build` ≈ 5–47 s, `pnpm test:e2e` ≈ 3 min, `pnpm bench` ≈ 3–5 min. Greps that show a result: `pnpm build` → `grep -iE "app.js|gzip|Tizen bundle OK|ERROR"`; `pnpm test:e2e` → `grep -iE "passed|failed|flaky"`; `pnpm bench` → `grep -E "^\[bench\]"`.
- **[pattern]** Docblock-only edits are not free: they change a package's lint / typecheck inputs, so after a late round of prose edits inside `packages/*/src` re-run the gate rather than trusting the earlier green. With turbo's cache it costs ~30 s lint + ~19 s typecheck (8 of 9 packages cached).
- **[convention]** Test counts quoted in `shmup_progress.md` must come from the run that actually passed — write the row with a placeholder and fill it from the green run; a guess is always wrong. Current baselines (2026-09-16, after M3-03): root suite **695 files / 8,269 tests**, e2e **277 specs** (chromium + the Firefox determinism spec), bench 21 tests, `tools/input-probe` **20 files / 533 tests**.
- **[gotcha]** `pnpm format` / `pnpm format:check` / `pnpm lint` chained in one foreground Bash call routinely exceeds the 120 s default and the call returns **empty output with a `backgroundTaskId`** — the work is still running, not failed. Read the task's `.output` file afterwards rather than re-running the chain.
- **[pattern]** Long-running verification runs in one backgrounded shell that writes its own log and a done-marker, then block in a background Bash call with `until [ -f $SCR/phase2.done ]; do sleep 5; done; grep …`. A backgrounded task's own `.output` file stays **0 bytes until it exits**, so never poll *that* for size — block on a string the run prints at the end instead (`until grep -qE "Test Files" …/<id>.output; do sleep 5; done`), which works because the harness flushes the file progressively for piped output. A `cat`/`tail` of a not-yet-created log makes the Bash call fail with empty output — guard with `2>/dev/null` or wait on the marker.
- **[pattern]** Adding a host app means sweeping the host lists in the docs, not just adding a page: the ASCII host box and the "new host platform" extension row in `docs/dev/architecture.md`, the build-outputs and root-scripts tables in `docs/dev/build-test-deploy.md`, the profile / per-host tables in `docs/dev/input-profiles.md`, plus `repo-layout.md` and the root README. `grep -n "apps/tizen\b" docs/dev/*.md` finds most of them; a bare `grep -n "<newhost>"` returning nothing across those files means the sweep has not been done.
- **[pattern]** A brand-new test file is fastest written with `cat > path <<'TSEOF' … TSEOF` in the same Bash call that runs its suite (`… && pnpm --filter @shmup/<pkg> test 2>&1 | grep -E "× |Tests |AssertionError" -A 10 | head -30`). Model a new app's build-output test on `apps/tizen/test/build/tizen-build.test.ts` — read it first: the pattern is `vi.stubEnv('NODE_ENV', 'production')` around a programmatic `build()` from `vite` into an `mkdtempSync` dir, a 120 s `beforeAll` timeout, and `rmSync` in `afterAll`.
- **[convention]** The Tizen / webOS bundle figures quoted in `CHANGELOG.md` / `shmup_progress.md` come from the build's own line, never an estimate: `pnpm build 2>&1 | grep "bundle OK"` → `app.js 1532.1 KB (395.5 KB gzip of 512.0 KB)`. Re-run the build after the last edit and quote that run.
- **[gotcha]** When one app reads a file out of another app's folder (webOS reusing `apps/tizen/polyfills/` and `apps/tizen/scripts/check-bundle.mjs`), add those paths to `turbo.json`'s `globalDependencies` — Turborepo's per-package input hashing does not see across package boundaries, so the borrowing app's build cache would stay valid after the shared file changed. Say so in the borrowing config's docblock too.
- **[fix]** `git rebase origin/master` aborts with `error: cannot rebase: You have unstaged changes.` on a large in-progress step. Check `git log --oneline -1 origin/master` against `HEAD` first — when origin has not moved there is nothing to rebase, so skip it and go straight to the scoped `git add`.
- **[pattern]** Stage a big step with one explicit `git add <paths…>` list (new directories like `apps/webos` can be named whole) and then verify before committing: `git status --porcelain | grep -v "^A \|^M " | head` must print nothing, and `git status --porcelain | awk '{print $1}' | sort | uniq -c` plus `git diff --cached --stat | tail -3` shows the added/modified counts. Never `git add -A` — the working tree carries untracked junk.
- **[gotcha]** `git status --porcelain` shows a brand-new directory as one line (`apps/webos/`); to see and count its files use `git status --porcelain --untracked-files=all <dir>`.
- **[gotcha]** A `python3 - <<'PY' … PY` edit whose `assert old in s` fails returns an **empty tool result** — no traceback, no exit code, nothing. Read `{}` as "the anchor did not match", not as success. Two causes, in order of likelihood: the anchor spans a line break that is not where you think, or the heredoc terminator was not alone on its line (`PY; tail -5 log` silently breaks the whole command — put the follow-up on the next line). Recover by probing first (`print(o in s)` per candidate line), then anchoring on **one line** and asserting `s.count(o) == 1`; confirm exact bytes with `sed -n 'N,Mp' file | cat -A`. This applies to TS docblocks exactly as it does to Markdown paragraphs.
- **[pattern]** When a change's headline benefit is a *ratio* (render p95 with a feature vs without), build the A/B into the bench itself — a creation option that restores the old behaviour (`createPixiRenderer({ renderGroups: false })`) plus a scenario that runs the same load both ways in one session. Comparing p95 across separate runs on a shared machine is noise. Quote the ratio as a **range over every run you have** (M3-02e's went 0.65–0.94× across runs). If your own verification run lands outside the quoted range, **widen the range and record the spread in every file** (`grep -rn "0.92" --include=*.md .`) rather than swapping in your single new number.

- **[pattern]** To prove a change is test-count-neutral (a docs/docblock-only fix), run the suite, then `git stash && pnpm test … ; git stash pop` and compare — it is the only way to attribute a count to the working tree rather than to the last commit.

- **[pattern]** Any *derived* figure in the docs (atlas pixels, glyph counts, budget ratios) must be recomputed from the real artifact before it is quoted or trusted. `assets/generated/atlas/main.json` gives the page size and the occupied area — sum `w*h` over `frames` — and `du -sb apps/<host>/dist` gives the dist figure. M3-03 shipped a CJK budget claim ("25 atlases, five 2048² pages, past `DIST_BUDGET`") that was wrong by 5–20×; the real numbers were 993,600 px vs 479,505 px occupied on one 1024² page. A wrong ratio in a doc that calls itself "the number that made this decision" is what the next reader will act on.
- **[convention]** When a doc's stated *reason* for a decision collapses under correct arithmetic, keep the decision and replace the reason with the true one — and fix every copy in the same commit. The same figure typically lives in five places: `docs/dev/<topic>.md`, the module docblock (`packages/core/src/**`), `shmup_plan.md`'s "As built" bullets, `shmup_progress.md`'s step row and `CHANGELOG.md`. Sweep with a content grep (`grep -rn -iE "6,?900|kanji|two orders of magnitude" --include=*.md --include=*.ts .`), not by memory of which files you touched.

- **[convention]** A host the project has no hardware for (`apps/webos`, Steamworks) ships with the "never run on hardware" warning repeated in **three** places — the package README, `shmup_plan.md`'s on-device checklist section, and the client doc — and its packaging CLI (`ares-package`, `tizen package`) is stood in for by a committed validator (`apps/webos/scripts/appinfo.mjs` mirrors `validateConfigXml`). Write the validator, never fake the run.
