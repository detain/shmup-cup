# Caliber Learnings

Accumulated patterns and anti-patterns from development sessions.
Auto-managed by [caliber](https://github.com/caliber-ai-org/ai-setup) — do not edit manually.

- **[pattern]** Before hooking or measuring a Pixi internal, read the installed source rather than guessing: `sed -n '1,90p' node_modules/.pnpm/pixi.js@<version>/node_modules/pixi.js/lib/rendering/renderers/shared/texture/TexturePool.mjs`. That is how the power-of-two rounding of `getOptimalTexture` and the `_texturePool` free-list shape were confirmed — the published typings do not show either.
- **[gotcha]** A Node-side unit-test fake of a Pixi global only covers the *creation* path. `test/e2e/render-profile.spec.ts` is what catches a counter that reads 0 in a real browser because the state existed before the counter started — when a debug figure is asserted in e2e, expect that spec to fail first and treat the Node tests as insufficient proof on their own.
- **[convention]** A new shipped code path that reuses an existing shader/program must be added to the e2e compile check (`test/e2e/mode7.spec.ts` compiles every vertex/fragment pairing in a real WebGL1 context) *alongside* the old pairing, not in place of it — the escape-hatch path still ships and still has to link on Chromium 69.
- **[convention]** A plan step's outcome is recorded as an `- **As built:**` block appended directly after that step's `- **Refs:**` line in `shmup_plan.md`, with one nested bullet per area; each bullet's bold lead sentence names the trap ("**The warm-up broke the overlay's `RT` figure, and the fix is in the meter.**"), then says which test caught it. The same finding is mirrored into `CHANGELOG.md` and `shmup_progress.md` in the same commit. Beyond "what was left out and why" and "still manual", the strongest blocks also record **where the implementation deviated from the plan's wording and why** and **how a measured number must not be over-read**. Review fixes get their own nested bullet (`(review round 1)`) — do not rewrite the original prose.
- **[convention]** When a debug/overlay figure changes what it counts, update the figure's row in the `docs/dev/rendering-and-shell.md` table in the same commit — the table sentence is the only place its semantics are written down, and nothing in `pnpm test` checks that it matches the code.
- **[pattern]** When a measured number changes, sweep for **every** place it was written down before committing: `grep -rn "<the figure>" --include=*.md --include=*.ts . | grep -v node_modules`. One bench figure lived in the plan's As-built block, two `docs/dev/*.md` files and a module docblock; nothing in `pnpm test` checks that they agree.
- **[gotcha]** Even a *finished* `pnpm test` background task's `.output` may hold only Vitest's transform advisories and `[exited with code 0]`, with the `Test Files` / `Tests` summary lines missing entirely. `grep -E "Test Files|Tests "` then returns nothing, which looks like a failure. Re-run redirected to your own log file to get the counts; do not conclude the suite failed from an empty grep.
- **[gotcha]** A python heredoc replace that splices a multi-line block into the middle of a Markdown paragraph leaves the old sentence welded onto the new text's last line. After any block insertion, re-read the region (`sed -n 'A,Bp'`) and fix the seam — Prettier does not reflow Markdown prose, so nothing else will catch it.
- **[gotcha]** `pnpm test:e2e` under load can fail two `determinism.spec.ts` cases with `Test timeout of 60000ms exceeded while setting up "page"` — a machine-contention symptom, not a determinism regression. Confirm by re-running just that spec (`pnpm exec playwright test --config test/e2e/playwright.config.ts --project=chromium determinism`) and then the full suite on a quiet machine; do not start debugging hashes off the first failure.
- **[convention]** Test counts quoted in `shmup_progress.md` must come from the run that actually passed — an interrupted or contended `pnpm test:e2e` prints a smaller total (`261 passed` + 1 failed vs the true `262 passed`). Re-read the number from the green run before writing the row.
- **[gotcha]** A `for i in $(seq …); do … sleep 20; done` wait loop is itself foregrounded and will hit the tool timeout and get backgrounded, leaving a stray poller process. Prefer one foreground call with an explicit long `timeout` and a `grep`-on-sentinel loop; a finished background task's `.output` *is* readable once `[exited with code N]` appears in it.
- **[pattern]** A focused package run is `npx vitest run --root packages/<pkg> test/<module>` (≈ 6 s for render-pixi's nine debug files) — much faster than the root `pnpm test` for iterating on one module, and its summary line prints reliably.
- **[pattern]** When a code change makes a helper accept new state, widen the test's fake factory with an *optional* parameter (`fakePool(free?)`) and add the `@param` line to its docblock in the same edit — jsdoc lint fails the run otherwise, and the existing zero-argument call sites keep working unchanged.
- **[fix]** `git rebase` aborts with `error: cannot rebase: Your index contains uncommitted changes` when the step's work is still staged — a `git stash push -- <one file>` does not clear the rest of the index. Commit first, then `git fetch && git rebase origin/master`; never chain the rebase ahead of the commit in one `&&` line (and skip the rebase entirely when `git log --oneline origin/master -1` matches `git log --oneline -1`).
- **[pattern]** Finish a rebase non-interactively with `git -c core.editor=true rebase --continue` — without it the call opens an editor and the Bash tool hangs until it times out.
- **[pattern]** Resolving a rebase conflict in the long-prose docs: find the markers with `grep -n "^<<<<<<<\|^=======\|^>>>>>>>" <file>`, splice with a python heredoc that keeps **upstream's** rewritten section, then re-apply your step's changes onto that upstream text with asserting `rep(old, new)` replacements, and close with `grep -c "<<<<<<<" <file>` (must print 0) plus `npx prettier --check <file>`. `docs/dev/rendering-and-shell.md` is rewritten upstream often — expect to re-target your edits onto the new wording rather than keep your own copy of the section.
- **[gotcha]** A `git stash pop` after a conflicted rebase can re-conflict on a file you never named in `git stash push -- <path>` (the stash commit records the whole tree). Check `git status --short` for `UU`, take the rebased side with `git checkout HEAD -- <file>`, then `git stash drop` — a conflicted pop keeps the stash entry.
- **[convention]** A rebase rewrites the commit SHA, so write the `shmup_progress.md` step row with a literal `COMMIT_SHA` placeholder and fill it from `git log --oneline -1` in a follow-up `(+ this row fix)` edit. Fill the suite count from an actual `pnpm test` run, never an estimate — a guessed "16 new (8,027 in the suite)" was really 10 new / 8,021.
- **[gotcha]** After rebasing onto a `master` that added a plan step, the resume block at the top of `shmup_progress.md` merges textually but is numerically stale. Re-derive with `grep -c "^| M[0-9]-[0-9]" shmup_progress.md` and update "Done: N of M steps", the "Next steps" sentence and the "single batch of …" list together.
- **[convention]** A new browser-side benchmark or harness under `test/bench/` is **not** part of `pnpm test` (its own Vitest config) — but it still needs `test/tsconfig.json` updated to cover the new files, or `pnpm typecheck` skips them silently. Pair it with a headless `test/integration/*.test.ts` that reads the bench sources as text and asserts the claims only a browser run could otherwise verify.
- **[gotcha]** `pnpm test:e2e` under load can fail two `determinism.spec.ts` cases with `Test timeout of 60000ms exceeded while setting up "page"` — machine contention, not a determinism regression. Confirm by re-running just that spec (`pnpm exec playwright test --config test/e2e/playwright.config.ts --project=chromium determinism`, ~11 s for 73 tests), then the full suite on a quiet machine; do not start debugging hashes off the first failure.

- **[gotcha]** Do not poll a background Bash task by `until [ -s <its .output file> ]` from *another* background task — the poller's own output file is also empty until it exits, so you end up polling the poller. A backgrounded `pnpm …` task's `.output` can stay **0 bytes for its whole run**. Redirect yourself instead: `(pnpm test:e2e > $SCR/e2e.log 2>&1; echo "EXIT=$?" >> $SCR/e2e.log)` in the background, then poll from the foreground with `timeout 110 bash -c 'until grep -q "EXIT=" $SCR/e2e.log; do sleep 10; done'` — the sentinel is both the completion marker and the status, and the inner timeout stays under the 120 s tool limit.
- **[pattern]** The whole gate fits in a few Bash calls if you pass an explicit long `timeout` (900000–1800000) and tail/grep each stage. Current budget: `pnpm install --frozen-lockfile` ~35 ms, `pnpm format:check` ≈ 30 s, `pnpm lint` ≈ 30–85 s (uncached ≈ 1 m 21 s, 9 turbo tasks), `pnpm typecheck` ≈ 17–31 s, `pnpm test` ≈ 75 s–10 min under load, `pnpm build` ≈ 5–47 s, `pnpm test:e2e` ≈ 2.7–4 min (262 specs), `pnpm bench` ≈ 3 min (the render bench alone ≈ 2 min). Without an explicit timeout the chain dies at the 120 s default and only the first command's output survives.
- **[fix]** When a chained `pnpm format && pnpm lint && pnpm typecheck && pnpm test` call hits the 120 s tool timeout and returns *empty* stdout, do not re-run the chain — the harness backgrounds it and keeps going. `cat` the returned `backgroundTaskId`'s `.output` file instead; once `[exited with code N]` is in it, every stage's grep output is there.
- **[gotcha]** `pnpm test`'s unfiltered tail is only Vitest's per-project "Transform |<project>| transforming modules took Ns" advisory — `tail -25` shows six of those and **no** pass/fail line, which reads as a silent failure. Always `grep -E "Test Files|Tests |FAIL"` instead (current baseline: 668 files / 8,021 tests). Same for `pnpm build` → `grep -iE "app.js|gzip|Tizen bundle OK|ERROR"` (current: `app.js 1500.5 KB (386.8 KB gzip of 512.0 KB)`), and for `pnpm bench` → `grep -E "Test Files|Tests |FAIL|Duration"` plus `grep -E "^\[bench\]"`.
