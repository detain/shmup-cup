# Caliber Learnings

Accumulated patterns and anti-patterns from development sessions.
Auto-managed by [caliber](https://github.com/caliber-ai-org/ai-setup) — do not edit manually.

- **[gotcha]** `pnpm test 2>&1 | tail -30` shows only Vitest's transform-cache advisories, **not** the pass/fail summary — the counts scroll off above them. Always grep for `Tests  |Test Files|failed` instead of tailing, or you will end a run not knowing whether it passed.
- **[convention]** Test counts quoted in `shmup_progress.md` must come from the run that actually passed — write the row with a placeholder and fill it from the green run; a guess is always wrong. A build agent's guessed figure (`8,259` / 694 files) was off by ten tests and one file against the real run. Current baselines (2026-09-16, after M3-03): root suite **695 files / 8,269 tests**, e2e **277 specs** (chromium + the Firefox determinism spec), bench 4 files / 21 tests, `tools/input-probe` **20 files / 533 tests**.
- **[pattern]** To prove a change is test-count-neutral (a docs/docblock-only fix), run the suite, then `git stash && pnpm test … ; git stash pop` and compare — it is the only way to attribute a count to the working tree rather than to the last commit.
- **[convention]** The Tizen / webOS bundle figures quoted in `CHANGELOG.md` / `shmup_progress.md` come from the build's own line, never an estimate: `pnpm build 2>&1 | grep "bundle OK"`. Re-run the build after the last edit and quote that run.
- **[pattern]** Any *derived* figure in the docs (atlas pixels, glyph counts, budget ratios) must be recomputed from the real artifact before it is quoted or trusted. `assets/generated/atlas/main.json` gives the page size and the occupied area — sum `w*h` over `frames` — and `du -sb apps/<host>/dist` gives the dist figure. M3-03 shipped a CJK budget claim ("25 atlases, five 2048² pages, past `DIST_BUDGET`") that was wrong by 5–20×; the real numbers were 993,600 px vs 479,505 px occupied on one 1024² page. A wrong ratio in a doc that calls itself "the number that made this decision" is what the next reader will act on.
- **[convention]** When a doc's stated *reason* for a decision collapses under correct arithmetic, keep the decision and replace the reason with the true one — and fix every copy in the same commit. The same figure typically lives in five places: `docs/dev/<topic>.md`, the module docblock (`packages/core/src/**`), `shmup_plan.md`'s "As built" bullets, `shmup_progress.md`'s step row and `CHANGELOG.md`. Sweep with a content grep (`grep -rn -iE "6,?900|kanji|two orders of magnitude" --include=*.md --include=*.ts .`), not by memory of which files you touched.
- **[pattern]** Batch several one-anchor documentation edits into a single `python3 - <<'PY'` heredoc holding a list of `(path, old, new)` triples with `assert old in s, path` and `replace(old, new, 1)` — it prints `ok <path>` per file, so a silent empty result identifies exactly which anchor missed.
- **[pattern]** When a change's headline benefit is a *ratio* (render p95 with a feature vs without), build the A/B into the bench itself — a creation option that restores the old behaviour (`createPixiRenderer({ renderGroups: false })`) plus a scenario that runs the same load both ways in one session. Comparing p95 across separate runs on a shared machine is noise. Quote the ratio as a **range over every run you have** (M3-02e's went 0.65–0.94× across runs). If your own verification run lands outside the quoted range, **widen the range and record the spread in every file** rather than swapping in your single new number.
- **[pattern]** Docblock-only edits are not free: they change a package's lint / typecheck inputs, so after a late round of prose edits inside `packages/*/src` re-run the gate rather than trusting the earlier green. With turbo's cache it costs ~30 s lint + ~28 s typecheck.
- **[convention]** A host the project has no hardware for (`apps/webos`, Steamworks) ships with the "never run on hardware" warning repeated in **three** places — the package README, `shmup_plan.md`'s on-device checklist section, and the client doc — and its packaging CLI (`ares-package`, `tizen package`) is stood in for by a committed validator (`apps/webos/scripts/appinfo.mjs` mirrors `validateConfigXml`). Write the validator, never fake the run.
- **[env]** `pnpm bench` must be run **alone on an idle machine** — zone-I's ms/tick budget flakes under CPU contention, so never overlap it with `pnpm test` or a build in another shell.
- **[pattern]** Long-running verification runs in one backgrounded shell that writes its own log and a done-marker, then block in a background Bash call with `until [ -f $SCR/phase2.done ]; do sleep 5; done; grep …`. A backgrounded task's own `.output` file stays **0 bytes until it exits**, so never poll *that* for size — block on a string the run prints at the end instead. A `cat`/`tail` of a not-yet-created log makes the Bash call fail with empty output — guard with `2>/dev/null` or wait on the marker.
- **[convention]** Test counts quoted in `shmup_progress.md` / `CHANGELOG.md` must come from the run that actually passed — write the row with a placeholder and fill it from the green run; a guess is always wrong. Current baselines (2026-09-16, after the M3-03 test round): root suite **706 files / 8,394 tests**, e2e **282 specs** (chromium + the Firefox determinism spec), bench 4 files / 21 tests, `tools/input-probe` **20 files / 533 tests**.
- **[pattern]** A backgrounded Bash task whose command is a **pipe into `grep`** buffers: its `.output` file stays **0 bytes until the process exits**, so `tail`/`ls -la` on it tells you nothing and "empty" never means "failed". Block on the exit marker instead — `until grep -q "exited with code" <task>.output; do sleep 8; done; cat <task>.output` — run as a Monitor or a second background call. Polling it with repeated `tail` calls every few seconds is pure waste.
- **[pattern]** Long-running verification runs in one backgrounded shell that writes its own log and a done-marker; guard any `cat`/`tail` of a not-yet-created log with `2>/dev/null` or the Bash call fails with empty output.
- **[env]** `pnpm bench` must be run **alone on an idle machine** — zone-I's ms/tick budget flakes under CPU contention, so never overlap it with `pnpm test` or a build in another shell. Check `uptime` before trusting a marginal result; this box has run the full gate at load average 30+.
- **[pattern]** Batch several one-anchor documentation edits into a single `python3 - <<'PY'` heredoc holding `(path, old, new)` triples with `assert old in s, path` and `replace(old, new, 1)` — it prints `ok <path>` per file, so a silent empty result identifies exactly which anchor missed. Pair the heredoc with `pnpm format:check` in the same call: Prettier skips Markdown, but the call proves the edit landed without a separate round trip.
- **[gotcha]** A `python3 - <<'PY' … PY` edit whose `assert old in s` fails returns an **empty tool result** — no traceback, no exit code. Read `{}` as "the anchor did not match", not as success. Usual causes: the anchor spans a line break that is not where you think, or the heredoc terminator was not alone on its line. Recover by probing (`print(o in s)` per candidate line), anchoring on **one line**, and asserting `s.count(o) == 1`.
- **[convention]** Adding a test file means adding its row to `test/README.md` — one row per file in the table, grouped by `integration/` / `scripts/` / `e2e/` prefix. Nothing enforces it (`grep -rn "test/README" test/integration/*.ts` finds no validator), so it is a review-only rule that is easy to forget; insert the new row **above** an existing anchor row with the batched-heredoc pattern above.
- **[pattern]** Adding a host app means sweeping the host lists in the docs, not just adding a page: the ASCII host box and the "new host platform" extension row in `docs/dev/architecture.md`, the build-outputs and root-scripts tables in `docs/dev/build-test-deploy.md`, the profile / per-host tables in `docs/dev/input-profiles.md`, plus `repo-layout.md` and the root README. It also changes what `pnpm test:e2e` builds — update the `pnpm test:e2e` row of `build-test-deploy.md` when a host joins the `turbo run build:test` list. `grep -n "apps/tizen\b" docs/dev/*.md` finds most of them.
- **[gotcha]** ESLint's compat floor is **Chromium 69** (`.browserslistrc`), but webOS 5 runs **Chromium 68** — `[].flat()` / `.flatMap()` pass the lint and would throw on an LG set. `test/integration/tv-engine-floor.test.ts` is the only thing catching those; run it (not just `pnpm lint`) after touching shipped runtime source.
- **[pattern]** A brand-new test file is fastest written with `cat > path <<'TSEOF' … TSEOF` in the same Bash call that runs its suite (`… && npx vitest run --project <proj> <file> 2>&1 | tail -15`). For a targeted re-run of a handful of integration files, `npx vitest run --project integration <files…>` finishes in ~2 s versus minutes for the full suite — use it after every doc/CHANGELOG edit that a doc-consistency test reads.
- **[convention]** Documentation edits are covered by tests: `integration/e2e-docs.test.ts`, `integration/tooling-config.test.ts`, `integration/cjk-budget.test.ts` and `integration/tv-engine-floor.test.ts` read the Markdown. After editing `CHANGELOG.md`, `docs/dev/build-test-deploy.md`, `shmup_progress.md` or `test/README.md`, re-run that set before assuming the gate is still green.
- **[pattern]** Stage a big step with one explicit `git add <paths…>` list and verify before committing: `git status --short` must show only the intended `A `/`M ` rows, and `git status --porcelain | grep '^??'` beforehand enumerates the new files to name. Never `git add -A` — the working tree carries untracked junk. Confirm build outputs are ignored with `git check-ignore -v <dir>` rather than trusting `.gitignore` by memory.
- **[pattern]** Draft a long commit message to a scratchpad file (`cat > …/commit-msg.txt <<'EOF' … EOF`) and commit with `-F`, rather than inlining a multi-paragraph `-m`; it keeps em-dashes, backticks and blank lines intact and lets you re-read it before committing.
- **[pattern]** A service object whose methods may be destructured (`const { syncAchievements } = steam`) must call its siblings as closures, not through `this` — write the test that destructures every method (a fake that asserts its own `this` on each call) so the trap is caught at the boundary rather than at runtime.
