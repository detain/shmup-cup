# Caliber Learnings

Accumulated patterns and anti-patterns from development sessions.
Auto-managed by [caliber](https://github.com/caliber-ai-org/ai-setup) — do not edit manually.

- **[pattern]** Any *derived* figure in the docs (atlas pixels, glyph counts, budget ratios, dist size) must be recomputed from the real artifact before it is quoted — `assets/generated/atlas/main.json` gives the page size and the occupied area (sum `w*h` over `frames`), the build check's own line gives the dist figure. When a doc's stated *reason* for a decision collapses under correct arithmetic, keep the decision, replace the reason, and fix every copy in the same commit (typically `docs/dev/<topic>.md`, the module docblock, `shmup_plan.md`, `shmup_progress.md`, `CHANGELOG.md`) — sweep with a content grep, not by memory. Better still, turn the arithmetic into a test that recomputes it and asserts the documents agree (`test/integration/cjk-budget.test.ts` does).
- **[pattern]** Batch several one-anchor documentation edits into a single `python3 - <<'PY'` heredoc holding a list of `(path, old, new)` triples with `assert old in s, path` and `replace(old, new, 1)` — it prints `ok <path>` per file, so a silent empty result identifies exactly which anchor missed. Pair the heredoc with `pnpm format:check` in the same call: Prettier skips Markdown, but the call proves the edit landed without a separate round trip.
- **[gotcha]** A python heredoc replacement that splices a long sentence into an existing paragraph leaves an over-100-column line, and Prettier does **not** reflow it (Markdown is excluded, and it won't wrap prose in `.md` files that are checked). Re-wrap the replacement text by hand to ≤100 columns in the same edit, or `pnpm format:check` passes while the line stays too long.
- **[pattern]** After doc edits, `pnpm exec prettier --write <the files you touched>` then re-run the doc-consistency tests in one call — `pnpm exec vitest run test/integration/cjk-budget.test.ts test/integration/tv-engine-floor.test.ts test/integration/localization.test.ts` finishes in seconds versus minutes for the full suite.
- **[convention]** Documentation edits are covered by tests: `integration/e2e-docs.test.ts`, `integration/tooling-config.test.ts`, `integration/cjk-budget.test.ts`, `integration/localization.test.ts` and `integration/tv-engine-floor.test.ts` read the Markdown. After editing `CHANGELOG.md`, `docs/dev/build-test-deploy.md`, `docs/dev/asset-pipeline.md`, `shmup_plan.md`, `shmup_progress.md` or `test/README.md`, re-run that set before assuming the gate is still green.
- **[convention]** Never write "nothing newer than Chrome 69" in a webOS source docblock or README — the floor there is **68**. When a source comment or README states an engine claim, state which of the three things it is about (emitted syntax, runtime APIs, or the `globalThis` polyfill) and point at `docs/dev/conventions.md` § "Two TVs, two engines" plus `tv-engine-floor.test.ts`; conflating them is the trap that produced a wrong claim in `apps/webos/src/main.ts` and `apps/webos/vite.config.ts`.
- **[convention]** Player-facing status pages (`docs/client/release-candidate.md`, `preview-build.md`) and `shmup_plan.md`'s status banner must not let "the code is finished" read as "the product shipped". Say plainly what has never run on hardware, never been submitted and is still a placeholder, and link `docs/client/outstanding-work.md`. Sweep with `grep -rn "is verified\|verified on\|has been tested on\|runs on the TV" docs/ README.md CHANGELOG.md` before claiming anything is checked.
- **[pattern]** Docblock-only edits are not free: they change a package's lint / typecheck inputs, so after a late round of prose edits inside `packages/*/src` or `apps/*/src` re-run the gate rather than trusting the earlier green (~30 s lint, ~26 s typecheck, and `pnpm test:e2e` ~3 min with turbo's cache).
- **[pattern]** Run the whole gate as one chained command into a log file and grep it — `(pnpm format:check && pnpm lint && pnpm typecheck && pnpm test && pnpm build) > <scratch>/final.log 2>&1; echo "EXIT=$?"; grep -E "Test Files|Tests  |bundle OK|All matched" <scratch>/final.log` — the `EXIT=` line is the only reliable pass/fail signal, and the greps give you the exact counts and bundle figures to quote.
- **[pattern]** Long-running verification runs in one backgrounded shell that writes its own log and a done-marker; guard any `cat`/`tail` of a not-yet-created log with `2>/dev/null` or the Bash call fails with empty output. A backgrounded task's own `.output` file stays **0 bytes until the process exits** (especially when the command is a pipe into `grep`), so never poll it for size — block on the exit marker instead: `until grep -q "exited with code" <task>.output; do sleep 8; done; cat <task>.output`.
- **[convention]** Adding a test file means adding its row to `test/README.md` — one row per file in the table, grouped by `integration/` / `scripts/` / `e2e/` prefix. Nothing enforces it, so it is a review-only rule that is easy to forget; insert the new row **above** an existing anchor row with the batched-heredoc pattern above.
- **[convention]** A host the project has no hardware for (`apps/webos`, Steamworks, the itch.io packer) ships with the "never run on hardware" warning repeated in **three** places — the package README or the script's own docblock, `shmup_plan.md`'s on-device checklist section, and the client doc — and its packaging CLI (`ares-package`, `tizen package`, butler) is stood in for by a committed validator (`apps/webos/scripts/appinfo.mjs` mirrors `validateConfigXml`). Write the validator, never fake the run.
- **[pattern]** A brand-new test file is fastest written with `cat > path <<'TSEOF' … TSEOF` in the same Bash call that runs its suite (`… && npx vitest run --project <proj> <file> 2>&1 | tail -15`). For a targeted re-run of a handful of integration files, `npx vitest run --project integration <files…>` finishes in ~2 s versus minutes for the full suite.
- **[convention]** Third-party version facts that a doc leans on (LG's webOS → Chromium table, a vendor spec page) are quoted with the **source link and the date you re-checked it** (`re-checked 2026-09-16: 4.x = 53, 5.x = 68, 6.x = 79`), in every copy — the package README, `docs/dev/conventions.md` and the module docblock — so the next reader knows how stale the claim is.
- **[env]** `pnpm bench` must be run **alone on an idle machine** — zone-I's ms/tick budget flakes under CPU contention, so never overlap it with `pnpm test`, `pnpm test:e2e` or a build in another shell. Check `uptime` / `pgrep -fc playwright` before trusting a marginal result; this box has run the full gate at load average 30+.
- **[gotcha]** CI's `test` job runs **only** `pnpm install --frozen-lockfile` then `pnpm test --shard=N/3` — it never runs `pnpm assets` or `pnpm build`. `assets/generated/**` is gitignored (`.gitignore:16`), so any test that reads `assets/generated/atlas/main.json` (or a `dist/`) passes locally off a stale artifact and fails on every clean checkout with `ENOENT`. Same for the three shards: whatever a test needs, it must produce itself.
- **[fix]** A test that needs the atlas imports `buildAtlas()` from `scripts/assets/pipeline.mjs` and reads `manifest` / `pages[0].png.length` in memory — deterministic, ~0.6 s, byte-identical to what `pnpm assets` writes (verified: same frames, same 136,592-byte PNG). That is what `apps/tizen/test/build/tizen-build.test.ts`, `apps/webos/test/build/webos-build.test.ts` and `test/integration/localization.test.ts` already do; copy them rather than `readFileSync`-ing the generated folder. Never "fix" it by skipping when the artifact is absent — a silently-skipped consistency test is worse than none.
- **[pattern]** To reproduce a CI failure exactly (no generated assets, no build output) without destroying your working tree, use a throwaway detached worktree: `git worktree add /tmp/<scratch>/clean HEAD --detach && cd … && pnpm install --frozen-lockfile` (~1 s, the store is shared) and run the suite there. `ls -a assets/generated/` in it shows only `.gitkeep`, which is precisely what the runner checks out.
- **[gotcha]** The root Vitest project covering `test/**` is named **`integration`**, not `test` (the *directory* is `test`). `vitest run --project test …` dies with "No projects were found"; just pass the file paths, or `--project integration`.
- **[gotcha]** `gh run view --job <jobId> --log-failed` can return **empty output** even for a job that clearly failed; `gh run view <runId> --log-failed | grep -iE "FAIL|Error:|Test Files"` returns the real failure. Query at the run level, not the job level.

It also changes what `pnpm test:e2e` builds — update that row of `build-test-deploy.md` when a host joins the `turbo run build:test` list. `grep -n "apps/tizen\b" docs/dev/*.md` finds most of them.
