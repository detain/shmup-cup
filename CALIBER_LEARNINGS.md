# Caliber Learnings

Accumulated patterns and anti-patterns from development sessions.
Auto-managed by [caliber](https://github.com/caliber-ai-org/ai-setup) — do not edit manually.

- **[convention]** A rebase rewrites the commit SHA, so write the `shmup_progress.md` step row with a literal `COMMIT_SHA` placeholder and fill it from `git log --oneline -1` in a follow-up `(+ this row fix)` edit. Fill the suite count from an actual `pnpm test` run, never an estimate — a guessed "16 new (8,027 in the suite)" was really 10 new / 8,021.
- **[gotcha]** After rebasing onto a `master` that added a plan step, the resume block at the top of `shmup_progress.md` merges textually but is numerically stale. Re-derive with `grep -c "^| M[0-9]-[0-9]" shmup_progress.md` and update "Done: N of M steps", the "Next steps" sentence and the "single batch of …" list together.
- **[convention]** A new browser-side benchmark or harness under `test/bench/` is **not** part of `pnpm test` (its own Vitest config) — but it still needs `test/tsconfig.json` updated to cover the new files, or `pnpm typecheck` skips them silently. Pair it with a headless `test/integration/*.test.ts` that reads the bench sources as text and asserts the claims only a browser run could otherwise verify.
- **[gotcha]** `pnpm test:e2e` under load can fail two `determinism.spec.ts` cases with `Test timeout of 60000ms exceeded while setting up "page"` — machine contention, not a determinism regression. Confirm by re-running just that spec (`pnpm exec playwright test --config test/e2e/playwright.config.ts --project=chromium determinism`, ~11 s for 73 tests), then the full suite on a quiet machine; do not start debugging hashes off the first failure.
- **[pattern]** When a measured number changes, sweep for **every** place it was written down before committing: `grep -rn "<the figure>" --include=*.md --include=*.ts . | grep -v node_modules`. One bench figure lived in the plan's As-built block, two `docs/dev/*.md` files (one a results-table header) and a module docblock; nothing in `pnpm test` checks that they agree.
- **[convention]** A plan step's outcome is recorded as an `- **As built:**` block appended directly after that step's `- **Refs:**` line in `shmup_plan.md`, one nested bullet per area, each bullet's bold lead sentence naming the trap ("**The warm-up broke the overlay's `RT` figure, and the fix is in the meter.**") and then which test caught it. The same finding is mirrored into `CHANGELOG.md` and `shmup_progress.md` in the same commit. Beyond "what was left out and why" and "still manual", the strongest blocks record **where the implementation deviated from the plan's wording and why** and **how a measured number must not be over-read**. Review fixes get their own nested bullet (`(review round 1)`) — do not rewrite the original prose.
- **[gotcha]** Do not poll a background Bash task by `until [ -s <its .output file> ]` from *another* background task — the poller's own output file is also empty until it exits, so you end up polling the poller. A backgrounded `pnpm …` task's `.output` can stay **0 bytes for its whole run**. Redirect yourself instead: `(pnpm test:e2e > $SCR/e2e.log 2>&1; echo "EXIT=$?" >> $SCR/e2e.log)` in the background, then poll from the foreground with `timeout 110 bash -c 'until grep -q "EXIT=" $SCR/e2e.log; do sleep 10; done'` — the sentinel is both the completion marker and the status, and the inner timeout stays under the 120 s tool limit.
- **[pattern]** The whole gate fits in a few Bash calls if you pass an explicit long `timeout` (900000–1800000) and tail/grep each stage. Current budget: `pnpm install --frozen-lockfile` ~35 ms, `pnpm format:check` ≈ 30 s, `pnpm lint` ≈ 30–85 s (uncached ≈ 1 m 21 s, 9 turbo tasks), `pnpm typecheck` ≈ 17–31 s, `pnpm test` ≈ 75 s–10 min under load, `pnpm build` ≈ 5–47 s, `pnpm test:e2e` ≈ 2.7–4 min (262 specs), `pnpm bench` ≈ 3 min (the render bench alone ≈ 2 min). Without an explicit timeout the chain dies at the 120 s default and only the first command's output survives.
- **[fix]** When a chained `pnpm format && pnpm lint && pnpm typecheck && pnpm test` call hits the 120 s tool timeout and returns *empty* stdout, do not re-run the chain — the harness backgrounds it and keeps going. `cat` the returned `backgroundTaskId`'s `.output` file instead; once `[exited with code N]` is in it, every stage's grep output is there.
- **[gotcha]** `pnpm test`'s unfiltered tail is only Vitest's per-project "Transform |<project>| transforming modules took Ns" advisory — `tail -25` shows six of those and **no** pass/fail line, which reads as a silent failure. Always `grep -E "Test Files|Tests |FAIL"` instead (current baseline: 668 files / 8,021 tests). Same for `pnpm build` → `grep -iE "app.js|gzip|Tizen bundle OK|ERROR"` (current: `app.js 1500.5 KB (386.8 KB gzip of 512.0 KB)`), and for `pnpm bench` → `grep -E "Test Files|Tests |FAIL|Duration"` plus `grep -E "^\[bench\]"`.
- **[gotcha]** Even a *finished* `pnpm test` background task's `.output` may hold only the transform advisories and `[exited with code 0]`, with the `Test Files` / `Tests` summary missing entirely, so the grep returns nothing and looks like a failure. Re-run redirected to your own log file to get the counts; do not conclude the suite failed from an empty grep.
- **[pattern]** Before hooking or measuring a Pixi internal, read the installed source rather than guessing: `sed -n '1,90p' node_modules/.pnpm/pixi.js@<version>/node_modules/pixi.js/lib/rendering/renderers/shared/texture/TexturePool.mjs`. That is how the power-of-two rounding of `getOptimalTexture` and the `_texturePool` free-list shape were confirmed — the published typings show neither.
- **[convention]** When a debug/overlay figure changes what it counts, update that figure's row in the `docs/dev/rendering-and-shell.md` table in the same commit — the table sentence is the only place its semantics are written down, and nothing in `pnpm test` checks that it matches the code.
- **[gotcha]** `test/e2e/*.spec.ts` runs against the *built* test bundles, not the sources: after editing anything under `packages/*/src` you must `pnpm --filter @shmup/web build:test` (and the Tizen test build for its file:// specs) before re-running Playwright, or you are re-testing the previous bundle and will conclude the change had no effect.
- **[pattern]** Validate every new pixel/shader e2e assertion by mutation: `cp <file> $SCR/<file>.bak`, splice a one-line break with a python heredoc that `assert`s the old text is present, `build:test`, re-run only that spec, then restore from the backup and rebuild. Half-pixel and vignette-scale breaks (`clip + vec2(1.0/uResolution.x, 0.0)`, `uHalf.zw` → `uHalf.xy`, `vScreen + vec2(0.0, 1.0)`) each failed exactly one new test and nothing else in the suite — that is the evidence the assertion is worth committing, and the commit message records it.
- **[pattern]** A focused Playwright run is `timeout 600 pnpm exec playwright test --config test/e2e/playwright.config.ts --project=chromium <file-fragment>` (≈ 11 s for one spec's 8 tests) — far faster than `pnpm test:e2e`, which rebuilds both hosts and runs ~266 specs in 3–4 min.
- **[gotcha]** Playwright's own summary (`  266 passed (3.6m)`) is printed only at the very end, so mid-run tails always look unfinished and an unanchored `grep -E "passed|failed"` matches nothing. Poll on the anchored sentinel `^  [0-9]+ (passed|failed)` (or your own `exit=` marker appended after the command) — never on the per-test ✓ lines.
- **[gotcha]** Under heavy load (`uptime` load average ~45, ~50 vitest forks) `pnpm test` reports `[vitest-pool]: Timeout terminating forks worker` and `test/scripts/audio-preview.test.ts` fails at its 60 s limit; the same file passes in ~13 s alone (`pnpm vitest run --project integration scripts/audio-preview.test.ts`). Re-run the individual file before treating it as a regression, and do not start `pnpm test`, `pnpm test:e2e` and `pnpm bench` concurrently — they starve each other.
- **[gotcha]** In render-pixi tests, Pixi v8 types `Container.children` as `Container[]` (so `child as Container` trips `@typescript-eslint/no-unnecessary-type-assertion` in `pnpm lint`) while `view.parent` is `Container | null` (so it needs `as Pixi.Container` or `tsc` fails with TS18047). Lint and typecheck bite from opposite directions here — run both after touching a test that walks the scene graph.
- **[fix]** `git rebase origin/master` aborts with `error: cannot rebase: You have unstaged changes` when the step's files are still unstaged — in an `&&` chain put `git add <files>` *before* the rebase, and skip the rebase entirely when `git log --oneline origin/master -1` equals `git log --oneline -1`.
- **[pattern]** When teardown is the thing under test, remember `bindWorld(null)` only *hides* the effect passes' nodes — the Mode-7 mesh, its geometry/shader/GlProgram and the second-pass `screen` container with its side panels are the passes' own and must be destroyed explicitly in `PixiRenderer.destroy()`. Any new pass added to the renderer needs its own line there plus a regression test that fails without it.
- **[pattern]** Before hooking or measuring a Pixi internal, read the installed source rather than guessing: `sed -n '1,90p' node_modules/.pnpm/pixi.js@<version>/node_modules/pixi.js/lib/rendering/renderers/shared/texture/TexturePool.mjs`. That is how the power-of-two rounding of `getOptimalTexture` and the `_texturePool` free-list shape were confirmed — the published typings show neither. The same trick pins a hand-written shader against `roundPixelsBitGl` / `globalUniformsBitGl` / `MeshGeometry` so a Pixi bump cannot silently zero a uniform.
- **[gotcha]** Even a *finished* `pnpm test` background task's `.output` may hold only Vitest's transform advisories and `[exited with code 0]`, with the `Test Files` / `Tests` summary lines missing entirely, so `grep -E "Test Files|Tests "` returns nothing and looks like a failure. Re-run redirected to your own log file to get the counts; do not conclude the suite failed from an empty grep.
- **[convention]** Test counts quoted in `shmup_progress.md` must come from the run that actually passed — an interrupted or contended run prints a smaller total. Re-read the number from the green run before writing the row.
- **[gotcha]** Do not poll a background Bash task by `until [ -s <its .output file> ]` from *another* background task — the poller's own output file is also empty until it exits, so you end up polling the poller, and a backgrounded `pnpm …` task's `.output` can stay **0 bytes for its whole run**. Redirect yourself instead: `(pnpm test:e2e > $SCR/e2e.log 2>&1; echo "EXIT=$?" >> $SCR/e2e.log)` in the background, then poll from the foreground with `timeout 110 bash -c 'until grep -q "EXIT=" $SCR/e2e.log; do sleep 10; done'`. Never fill the wait with `echo ok` no-op calls — one sentinel loop replaces dozens of them.
- **[pattern]** A focused package run is `npx vitest run --root packages/<pkg> test/<module>` (≈ 3–6 s, and its summary line prints reliably) — much faster than the root `pnpm test` for iterating on one module. `pnpm --filter @shmup/render-pixi exec vitest run test/<path>` works the same way for a single file.
- **[fix]** `git rebase` aborts with `error: cannot rebase: Your index contains uncommitted changes` when the step's work is still staged — a `git stash push -- <one file>` does not clear the rest of the index. Commit first, then `git fetch && git rebase origin/master`; never chain the rebase ahead of the commit in one `&&` line.
- **[pattern]** Resolving a rebase conflict in the long-prose docs: find the markers with `grep -n "^<<<<<<<\|^=======\|^>>>>>>>" <file>`, splice with a python heredoc that keeps **upstream's** rewritten section, then re-apply your step's changes onto that upstream text with asserting `rep(old, new)` replacements, and close with `grep -c "<<<<<<<" <file>` (must print 0) plus `npx prettier --check <file>`. `docs/dev/rendering-and-shell.md` is rewritten upstream often — expect to re-target your edits onto the new wording.

Greps that actually show a result: `pnpm test` → `grep -E "Test Files|Tests |FAIL"`; `pnpm build` → `grep -iE "app.js|gzip|Tizen bundle OK|ERROR"`; `pnpm bench` → `grep -E "Test Files|Tests |exit="` plus `grep -E "^\[bench\]"`. The Tizen gzip figure can also be recomputed after a root build with `node -e "const{gzipSync}=require('node:zlib');console.log((gzipSync(require('node:fs').readFileSync('apps/tizen/dist/app.js')).length/1024).toFixed(1))"`.
