# Caliber Learnings

Accumulated patterns and anti-patterns from development sessions.
Auto-managed by [caliber](https://github.com/caliber-ai-org/ai-setup) — do not edit manually.

- **[gotcha]** Test *helpers* are linted with the same type-aware rules as sources. Two traps that bite repeatedly: a harness object literal whose shorthand method is later destructured trips `@typescript-eslint/unbound-method` — declare it as a property with an arrow (`readonly more: (d: readonly number[]) => number[]` / `more: (deltas) => {…}`) instead of `more(deltas) {…}`; and a ternary used as a statement (`cond ? a.push(x) : a.push(y)`) trips `@typescript-eslint/no-unused-expressions` — write `a.push(cond ? x : y)`.
- **[pattern]** For a long run whose result you need in full, redirect to a log file in the session scratchpad and background the Bash call (`pnpm test > …/scratchpad/full-test.log 2>&1; echo "exit=$?"; grep -aE "Test Files|Tests  " …`) — then pull the failure detail out of the log with `grep -a -A30 "Failed Tests" <log>`. The `-a` matters: Vitest's log has escape bytes and plain `grep` calls it a binary file.
- **[gotcha]** `apps/electron`'s `test/main/main.test.ts` (the F11 fullscreen / Ctrl+= scale `vi.waitFor` assertion) is flaky under the full `pnpm test` load — it passes on its own (`pnpm --filter @shmup/electron exec vitest run test/main/main.test.ts`, ~2 s) and on a second full run. Before chasing it, re-run the single file, then re-run `pnpm test`; only treat it as a real break if it fails twice.
- **[pattern]** `pnpm format:check && pnpm lint && pnpm typecheck` chained in one Bash call exceeds the 120 s foreground timeout unless you pass an explicit long `timeout` (e.g. 900000–1800000) and tail/grep each stage. Rough budget: `pnpm format:check` ≈ 30 s, `pnpm lint` ≈ 75 s uncached, `pnpm typecheck` ≈ 25 s, `pnpm build` ≈ 47 s (9 turbo tasks), `pnpm test` ≈ 76 s (659 files / 7958 tests), `pnpm test:e2e` ≈ 3.5 min (259 specs).
- **[gotcha]** Do not poll a background Bash task by `until [ -s <its .output file> ]` from *another* background task — the poller's own output file is also empty until it exits, so you end up polling the poller. Either poll from a foreground call with a long `timeout`, or wait on the real process (`until ! ps aux | grep -q "[v]itest run --project integration"; do sleep 5; done`), or use `Monitor` with `tail -f` on a log you redirected yourself.
- **[pattern]** A lint rule that only covers part of the tree needs a belt-and-braces source scan test beside it: `apps/web/src` switches `no-restricted-syntax` off wholesale (it may use `import.meta`), so a banned pattern there passes lint. `test/integration/eslint-rules.test.ts` pairs each fixture-snippet rule check with a `readdirSync` walk over every runtime `src/` tree asserting the offender list is empty.
- **[convention]** A plan step's outcome is recorded as an `- **As built:**` block appended directly after that step's `- **Refs:**` line in `shmup_plan.md`, with one nested bullet per area, and it explicitly records what was *left out* and why, plus anything still manual. Later review fixes get their own nested bullet (e.g. `- **Review fixes (round 1).** …`) naming the symptom and the call site — do not rewrite the original "As built" prose.
- **[gotcha]** Vitest's asymmetric matchers fail this repo's type-aware lint in tests: `expect(issues).toEqual([expect.objectContaining({ path: expect.stringContaining('x') })])` trips `@typescript-eslint/no-unsafe-assignment`. Write the assertion positionally — `expect(issues).toHaveLength(1); expect(issues[0].message).toBe(…)` — or compare against a plain `[{ path, message }]` literal.
- **[gotcha]** A lookup table written as a plain `Object.freeze({ … })` record still answers to `constructor`, `toString`, `valueOf`, and this repo's id patterns (e.g. `INPUT_PROFILE_ID_PATTERN = /^[a-z0-9]+(?:-[a-z0-9]+)*$/`) **accept** `constructor` — so an unguarded `TABLE[id]` on a user-supplied id returns a function. Guard every variable-key lookup with `Object.prototype.hasOwnProperty.call(TABLE, key)` (`Object.hasOwn` is banned for Chromium 69) and type-check the result. Audit new code with `git show <ref> -- 'packages/*/src/*' 'apps/*/src/*' | grep -E '^\+' | grep -E '\[[a-z][A-Za-z0-9_.]*\]'`.
- **[convention]** A regression test's reason is recorded twice: in the test file's top docblock (`Regression: <old behaviour> (now <new>)`, appended after any existing regression note) and as a comment inside the `it(...)` naming the exact mechanism. Extend an existing edge file's docblock summary rather than replacing it.
- **[pattern]** `pnpm vitest run <single test path>` works from the repo root against the multi-project config (≈ 0.4 s for one core file); `pnpm --filter <pkg> exec vitest run test/<module>/<file>.test.ts` is the per-package equivalent. Use them for the tight edit/test loop and save `pnpm test` for the final gate.
- **[pattern]** Stage a step's work with an explicit `git add <file> \\\n <file> …` list and confirm with `git status --porcelain`, never `git add -A` — the tree routinely carries unrelated modified/untracked files.
- **[convention]** A plan step's outcome is recorded as an `- **As built:**` block appended directly after that step's `- **Refs:**` line in `shmup_plan.md`, with one nested bullet per area, and it explicitly records what was *left out* and why, plus anything still manual (hardware / account checks). Later review fixes get their own nested bullet (e.g. `- **Review fixes (round 1).** …`) naming the symptom and the call site — do not rewrite the original "As built" prose.
- **[convention]** A finished step also updates `shmup_progress.md` in three places at once: the `## Current state — resume point (<date>)` block (date, "Done: N of M steps", the next steps, the `master` pointer), the step's own table row (`pending` → `done`, review rounds, new test count, the commit shas), and any "Infrastructure / input probe" note whose tense the step invalidated. Re-derive N/M from the file rather than trusting the old text: `grep -c "^| M[0-9]-[0-9]" shmup_progress.md` and `grep "^| M[0-9]-[0-9]" shmup_progress.md | grep -c "| done"`.
- **[pattern]** Edit long prose lines in Markdown/README/plan *and* TypeScript files with a `python3 - <<'PY'` heredoc that asserts the old substring exists before replacing (`assert old in s` / `assert s.count(anchor)==1`) — the anchors are 100-column wrapped sentences that are hard to match exactly with Edit, and the assert turns a silent no-op into a visible failure. Wrap it in a small `patch(path, [(old, new), …])` helper when touching several files in one call. Follow Markdown edits with `npx prettier --write <files>` (root Markdown *is* Prettier-checked by `pnpm format:check`).
- **[pattern]** To move a whole block inside a long Markdown file (e.g. re-ordering a README section), do it in python by `index()`-ing the block's start and the next heading, slicing it out and re-inserting it at an asserted anchor — then re-`grep -n` the three headings to confirm the new order. Editing around it in place drifts.
- **[pattern]** After renaming any user-visible label or content id, sweep the **whole** tree, sources included: `grep -rn "OLD LABEL" docs/ README.md apps/ packages/ content/ | grep -v node_modules | grep -v "/test/" | grep -v dist/`. Stale names survive in TSDoc `@example` snippets and module docblocks (`apps/tizen/src/boot/index.ts`, `packages/core/src/ui/index.ts`, `packages/input-web/src/rebind/index.ts`) that no test or lint rule checks.
- **[gotcha]** Editing TSDoc inside `packages/*/src` or `apps/*/src` is not a "docs-only" change: Prettier checks `.ts`, and the Tizen bundle budget is re-measured — re-run the full `format:check → lint → typecheck → test → build → test:e2e` gate after such an edit, not just `format:check`.
- **[fix]** Do not chain `git fetch && git rebase origin/master && git add …` before staging — the rebase aborts on a dirty working tree and the whole chain returns empty output with nothing done. Compare first (`git log --oneline origin/master -1` vs `git log --oneline -1`); when the remote has not moved, skip the rebase and stage directly.
- **[pattern]** Verify a new doc heading's anchor before linking to it: one chained `grep -n "^## <Heading>" <file> && grep -n "^### <Heading>" <file> && …` call over every file you added a cross-link to. Nothing in `pnpm test` checks doc links, and GitHub-slugged anchors with backticks/em-dashes are easy to get wrong.
- **[gotcha]** `pnpm test`'s unfiltered tail is only Vitest's per-project "Transform |<project>| transforming modules took Ns" advisory — `tail -25` shows six of those and **no** pass/fail line, which reads as a silent failure. Always `grep -E "Test Files|Tests |FAIL"` instead (current baseline: 659 files / 7,958 tests). Same for `pnpm build` → `grep -iE "app.js|gzip|Tizen bundle OK|ERROR"`.
- **[pattern]** The whole gate fits in a few Bash calls if you pass an explicit long `timeout` (900000–1800000) and tail/grep each stage. Current budget: `pnpm install --frozen-lockfile` ~35 ms, `pnpm format:check` ≈ 30 s, `pnpm lint` ≈ 80 s uncached, `pnpm typecheck` ≈ 26 s, `pnpm test` ≈ 75 s, `pnpm build` ≈ 18–47 s, `pnpm test:e2e` ≈ 3.5 min (259 specs). Without an explicit timeout the chain dies at the 120 s default and only the first command's output survives.
- **[gotcha]** `pnpm install --frozen-lockfile` is near-instant here (~35 ms, "resolution step is skipped") — running it before a gate costs nothing and rules out a stale link, so keep it at the head of the verification chain.
- **[pattern]** Re-check the Tizen size budgets without a rebuild: `node apps/tizen/scripts/check-bundle.mjs` (runs fine from the repo root, no `cd`) reads the existing `apps/tizen/dist/` and prints `Tizen bundle OK: app.js … KB (… gzip of 512.0 KB)`. Quote that gzip figure in CHANGELOG / progress rather than guessing.
- **[gotcha]** A bucket-picking helper written as a `<` chain silently mis-classifies `NaN` (every comparison is false, so it falls through to the overflow bucket). Write the chain negated — `if (!(ms >= edge)) return i;` — so a `NaN` lands in bucket 0, and check the `@example` in its docblock actually matches the edges.

- **[fix]** Wrapping a wait in a *background Bash* task (`until grep -q EXIT= log; do sleep 5; done`) does not help — that task's own output file is also empty until it exits, so you end up polling the poller. Use `Monitor` with `tail -f -n 0 "$LOG" | grep -E --line-buffered "<done marker>|✘|failed|Error:"` and a generous `timeout_ms`, or wait on the real process, or poll from a foreground call with a long `timeout`.
- **[pattern]** A background research/review Agent's full report lives in its raw task output file (`/tmp/claude-*/…/tasks/<task-id>.output`, JSONL of message events), not just in the notification excerpt. Extract the last assistant `text` block with a small `python3` pass over the lines and write it to a scratchpad `.md` before the notification text scrolls away.
