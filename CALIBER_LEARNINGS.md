# Caliber Learnings

Accumulated patterns and anti-patterns from development sessions.
Auto-managed by [caliber](https://github.com/caliber-ai-org/ai-setup) — do not edit manually.

- **[convention]** Test counts quoted in `shmup_progress.md` must come from the run that actually passed — write the row with a placeholder and fill it from the green run; a guess is always wrong. Current baselines: root suite **674 files / 8,098 tests**, 266 e2e specs, `pnpm bench` 4 files / 19 tests, shell project 63 files / 457 tests, `tools/input-probe` 18 files / 511 tests.
- **[pattern]** The whole gate fits in a few Bash calls if you pass an explicit long `timeout` (900000–1800000) and grep each stage; without one the chain dies at the 120 s default and only the first command's output survives. Current budget: `pnpm format:check` ≈ 30 s, `pnpm lint` ≈ 21–88 s (9 turbo tasks), `pnpm typecheck` ≈ 17–35 s, `pnpm test` ≈ 100 s–10 min under load, `pnpm build` ≈ 5–47 s, `pnpm test:e2e` ≈ 3.5 min, `pnpm bench` ≈ 3–5 min. Greps that show a result: `pnpm test` → `grep -E "Test Files|Tests |FAIL"`; `pnpm build` → `grep -iE "app.js|gzip|Tizen bundle OK|ERROR"`; `pnpm test:e2e` → `grep -iE "passed|failed|flaky"`; `pnpm bench` → `grep -E "^\[bench\]"`.
- **[gotcha]** A piped `pnpm test 2>&1 | tail -N` is unreliable: sometimes it shows `Test Files` / `Tests`, sometimes the pipe drops them and leaves only Vitest's transform advisories plus `[ELIFECYCLE] Test failed` while the harness records `[exited with code 0]`. Pipe to `grep -E "Test Files|Tests |FAIL"` (reliable) or redirect to a file — and never conclude the suite failed from an empty grep.
- **[gotcha]** Do not poll a background Bash task by `until [ -s <its .output file> ]` from *another* background task — the poller's own output file is also empty until it exits, and a backgrounded `pnpm …` task's `.output` can stay **0 bytes for its whole run**. Redirect yourself: `(pnpm test:e2e > $SCR/e2e.log 2>&1; echo "EXIT=$?" >> $SCR/e2e.log)` in the background, then poll with `until grep -q "^EXIT=" $SCR/e2e.log; do sleep 5; done`. Never fill the wait with `echo ok` no-ops.
- **[gotcha]** Under heavy load (`uptime` ~45, ~50 vitest forks) `pnpm test` reports `[vitest-pool]: Timeout terminating forks worker` and `test/scripts/audio-preview.test.ts` fails at its 60 s limit, and `pnpm test:e2e` can fail two `determinism.spec.ts` cases with `Test timeout of 60000ms exceeded while setting up "page"`. Re-run the single file/spec before treating either as a regression, and never start `pnpm test`, `pnpm test:e2e` and `pnpm bench` concurrently — they starve each other.
- **[gotcha]** `test/bench/zones.perf.ts` "zone I" is the canary of the bench suite: its median sits right at the 1 ms/tick budget and it fails (`expected 1.0573936 to be less than 1`) when `pnpm bench` shares the machine with `pnpm test:e2e`. **Always run `pnpm bench` alone on an idle machine**; re-run it alone before treating a zone tick-budget failure as a regression.
- **[pattern]** A focused Vitest project run from the repo root is `pnpm vitest run --project <shell|core|integration|…> 2>&1 | grep -E "Test Files|Tests |FAIL"`; a focused package run is `npx vitest run --root packages/<pkg> test/<module>` or `pnpm --filter @shmup/<pkg> exec vitest run test/<path>` (≈ 4 s for a single allocation guard). Keep `pnpm test` for the gate.
- **[pattern]** A focused Playwright run is `timeout 600 pnpm exec playwright test --config test/e2e/playwright.config.ts --project=chromium <file-fragment>` (≈ 11 s for one spec) — far faster than `pnpm test:e2e`, which rebuilds both hosts and runs 266 specs in ~3.5 min.
- **[gotcha]** Vitest does not type-check, so a test fixture that goes stale when you add a **required** field to an exported type still passes `pnpm test` and fails only `pnpm typecheck` (`error TS2741: Property 'hist' is missing …`). After widening a shared type in `packages/*/src`, run `pnpm typecheck` before believing a green focused test run — the hand-written sample/fixture factories in `packages/*/test/**` are where it bites.
- **[pattern]** Before hooking or measuring a Pixi internal, read the installed source rather than guessing: `sed -n '1,90p' node_modules/.pnpm/pixi.js@<version>/node_modules/pixi.js/lib/rendering/renderers/shared/texture/TexturePool.mjs`. The published typings show neither `getOptimalTexture`'s power-of-two rounding nor the `_texturePool` free-list shape.
- **[fix]** Do NOT quote a hand-computed gzip of the Tizen bundle. `node -e "gzipSync(readFileSync('apps/tizen/dist/app.js'))"` printed **397.4 KB** while the build printed `Tizen bundle OK: app.js 1500.5 KB (386.8 KB gzip of 512.0 KB)` — `check-bundle.mjs` measures the budgeted payload, the raw file is larger. The figure that goes into `CHANGELOG.md` / `shmup_progress.md` is the one from the `Tizen bundle OK:` line of a fresh build.
- **[fix]** `git rebase` aborts with `error: cannot rebase: You have unstaged changes` when the step's work is not yet staged — and chaining `git rebase … && git add …` in one command cannot help, because the rebase runs first. Use `git rebase --autostash origin/master` (what the review/fix agents run at start), or commit before rebasing; skip the rebase entirely when `git log --oneline origin/master -1` equals `git log --oneline -1`.
- **[convention]** A plan step's outcome is recorded as an `- **As built:**` block appended directly after that step's `- **Refs:**` line in `shmup_plan.md`, one nested bullet per area, each bullet's bold lead sentence naming the trap and then which test caught it. The same finding is mirrored into `CHANGELOG.md` and `shmup_progress.md` in the same commit. The strongest blocks record **where the implementation deviated from the plan's wording and why** and **how a measured number must not be over-read**. Review fixes get their own nested bullet (`(review round N)`) — do not rewrite the original prose.
- **[convention]** A per-frame/per-tick path stays measured, not asserted: when a fix adds work to a sampler, put the fold on the cold path (`close()` / the report timer) and prove `commitFrame`-style hot functions are **byte-for-byte unchanged** (`git show <sha> -- <file>`) plus run the guard alone (`pnpm --filter @shmup/shell exec vitest run test/telemetry/telemetry-alloc.test.ts`). Grep every `.close(` / `.report()` call site to confirm the cold path is the only caller.
- **[convention]** Test counts quoted in `shmup_progress.md` must come from the run that actually passed — write the row with a placeholder and fill it from the green run; a guess is always wrong. Current baselines: root suite **674 files / 8,098 tests**, e2e 267 specs (chromium + the Firefox determinism spec), `pnpm bench` 4 files / 19 tests, shell project 63 files / 457 tests, `tools/input-probe` 18 files / 511 tests.
- **[gotcha]** A backgrounded task's `.output` file stays **0 bytes for the whole run** and only fills when the task exits, so `tail` on it proves nothing about progress and a directory of `test-results/` entries is not a failure count (Playwright creates a folder per *attempt*, including passing retries/traces). To wait, block in one Bash call with an explicit timeout: `until [ -s <task>.output ]; do sleep 15; done; cat <task>.output`. Do not burn turns polling with `tail` + `pgrep` + `uptime`.
- **[gotcha]** `pgrep -fc playwright` counts browser helper processes, not remaining tests — it swings 40→80→40 while a run is healthy. The only trustworthy progress signals are the run's own final `N passed (Xm)` line and the wrapper `sh -c turbo run build:test … && playwright test` process's `ps -o etime`.
- **[env]** `test/e2e/playwright.config.ts` sets `retries: ci ? 1 : 0` — a local `pnpm test:e2e` has **zero retries**, so a single load-induced flake fails the whole run. Re-run the one spec (`pnpm exec playwright test --config test/e2e/playwright.config.ts --project=chromium <fragment>`) before calling it a regression.
- **[fix]** `git rebase` aborts with `error: cannot rebase: You have unstaged changes` when the step's work is not yet staged — and chaining `git rebase … && git add …` in one command cannot help, because the rebase runs first (the whole `&&` chain is lost). Check first: when `git log --oneline origin/master -1` equals `git log --oneline -1` there is nothing to rebase — just `git add` the step's files. Otherwise use `git rebase --autostash origin/master`.
- **[convention]** Always `git add` the step's files **by explicit path** (never `git add -A`) — the working tree carries untracked scratch files that must not be committed — and confirm with `git status --short` that only the intended `M`/`A` rows are staged.
- **[pattern]** Write the commit message to a scratchpad file first (`$SCR/commit-msg.txt`, then `git commit -F`) — these messages are multi-paragraph prose naming each new test file, the bug each suite caught, and how a measured number must not be over-read; composing them inline in a `git commit -m` heredoc loses the formatting and cannot be revised.
- **[pattern]** When an implementation or a figure's *definition* changes, sweep for the wording as well as the numbers before committing: `grep -rn "<phrase>" --include=*.md --include=*.mjs --include=*.ts docs tools packages test apps`. One M3-02f wording fix touched six files plus a test. Nothing in `pnpm test` checks that the prose agrees with the code.
- **[pattern]** Verify a statistics change by re-implementing it standalone in a throwaway `node` script under the scratchpad and comparing against the exact answer over synthetic data, rather than trusting the unit tests: M3-02f's pooled percentile was checked by re-coding `fold` + `percentileOf` and diffing pooled vs exact p50/p95 over 20 windows × 180 frames, and a worst-case payload was built the same way (400 windows × saturated histograms vs the receiver's 2 MiB cap). A unit test proves the code does what it does; this proves the *quantity* is the one claimed.
- **[convention]** Two quantile conventions coexist on purpose — the bench's `floor(q * n)` and the telemetry's `floor(q * (n - 1) + 0.5)`. They are **pinned, not unified**: changing the bench's would move p95s already published in `docs/dev/input-probe-results.md` §11.3 and the budgets tuned against them. Do not "harmonize" them.
- **[convention]** Never claim an on-device millisecond figure is "comparable" with a `pnpm bench` figure. The bench runs Chromium + SwiftShader on a shared desktop; only its **counted** quantities (draw calls, pooled render-target bytes, structure rebuilds, heap delta) and its **in-run ratios** transfer to the TV. The correct wording when two figures share a definition is "the same **statistic**, not a comparable **magnitude**" — say which, in every place the number is described.
- **[convention]** A per-frame/per-tick path stays measured, not asserted: when a fix adds work to a sampler, put the fold on the cold path (`close()` / the report timer) and prove `commitFrame`-style hot functions are **byte-for-byte unchanged** (`git show <sha> -- <file>`) plus run the guard alone (`pnpm --filter @shmup/shell exec vitest run test/telemetry/telemetry-alloc.test.ts`). A cheap way to pin "the measurement did not move onto the frame" is a spy over `%TypedArray%.prototype.sort` / `Array.prototype.sort` asserting zero calls across 1000 frames and exactly N per closed window.

- **[convention]** A receiver/formatter that prints untrusted JSON must route every interpolated nested value through a total `str()` helper — `{"toString": 1}` is valid JSON with no primitive form and throws inside a template literal, and a `verdicts` / `env` that is not an object throws on property access. The handler's `catch` keeps the process alive but silently loses the line the owner watches while capturing; a seeded-junk fuzz suite (`tools/input-probe/test/logServerFuzz.test.ts`) is what catches it.
