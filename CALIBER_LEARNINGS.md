# Caliber Learnings

Accumulated patterns and anti-patterns from development sessions.
Auto-managed by [caliber](https://github.com/caliber-ai-org/ai-setup) — do not edit manually.

- **[gotcha]** When a test asserts the *presence* of a bug ("`structureRebuilds` keeps rising every frame"), fixing the bug fails that test legitimately. Rewrite it to assert the fix **and** keep the original guarantee it was standing in for (the counter is still read in the right place — Pixi clears `structureDidChange` while rendering, so a misplaced read sits at 0 for ever), and say in the plan's "As built" that the test changed meaning.
- **[fix]** When such an `assert old in s` fails on a Markdown paragraph, the anchor almost always spans a line break that is not where you think. Shorten the anchor to **one line** and confirm the exact bytes first with `sed -n 'N,Mp' file | cat -A` (em-dashes and arrows show as `M-bM-^FM-^R`), rather than guessing at the wrap.
- **[gotcha]** Vitest does not type-check, so a test fixture that goes stale when you add a **required** field to an exported type still passes `pnpm test` and fails only `pnpm typecheck` (`error TS2741: Property 'hist' is missing …`). After widening a shared type (e.g. a new field on `RenderBenchResult`), run `pnpm typecheck` and fix every fixture literal before believing a green focused test run.
- **[convention]** Test counts quoted in `shmup_progress.md` must come from the run that actually passed — write the row with a placeholder and fill it from the green run; a guess is always wrong. Current baselines (2026-09-16, M3-02e): root suite **679 files / 8,143 tests**, e2e **267 specs** (chromium + the Firefox determinism spec), `pnpm bench` render scenarios all green, shell project 63 files / 457 tests, `tools/input-probe` **20 files / 533 tests**.
- **[fix]** `vitest run --project test …` fails with `No projects were found. The filter matched no projects: test` even though `vitest.config.ts` lists `'test'` in `projects` — that entry is a *directory*, and its project **name** comes from `defineShmupProject()` (it is `integration`). Either filter by the real name (`--project integration`) or just pass file paths.
- **[gotcha]** A bare `npx vitest run <paths>` from the root silently **drops paths that belong to another project** — passing three files reported `Test Files 2 passed (2)` with no warning. Always check the file count in the summary equals the number of files you named; run package files with `pnpm --filter @shmup/<pkg> exec vitest run test/<path>` instead.
- **[pattern]** Focused runs: a whole package project is `pnpm vitest run --project render-pixi` (≈ 14 s, 67 files); a single new suite is `pnpm vitest run --project <name> -t "<describe fragment>"` (prints `2 passed | 67 skipped`). The render bench alone is `pnpm exec vitest run --config test/bench/vitest.config.ts render.perf` (~2–3 min, so background it) and `-t "worst-case, CRT off"` narrows it to the two A/B scenarios (~30 s).
- **[pattern]** The whole gate fits in a few Bash calls if you pass an explicit long `timeout` (900000–1800000) and grep each stage; without one the chain dies at the 120 s default and only the first command's output survives. Current budget: `pnpm format:check` ≈ 30 s, `pnpm lint` ≈ 24–78 s, `pnpm typecheck` ≈ 29–35 s, `pnpm test` ≈ 100 s–10 min under load, `pnpm build` ≈ 5–47 s, `pnpm test:e2e` ≈ 3 min, `pnpm bench` ≈ 3–5 min. Greps that show a result: `pnpm build` → `grep -iE "app.js|gzip|Tizen bundle OK|ERROR"`; `pnpm test:e2e` → `grep -iE "passed|failed|flaky"`; `pnpm bench` → `grep -E "^\[bench\]"`.
- **[pattern]** Long-running verification runs in one backgrounded shell that writes its own log and a done-marker, then block in a background Bash call with `until [ -f $SCR/phase2.done ]; do sleep 5; done; grep …`. A backgrounded task's own `.output` file stays **0 bytes until it exits**, so never poll *that*; and a `cat`/`tail` of a not-yet-created log makes the Bash call fail with empty output — guard with `2>/dev/null` or wait on the marker.
- **[convention]** TSDoc `{@link X}` must never survive into a `.md` file — it renders literally. After copying docblock prose into docs, run `grep -rn "{@link" --include=*.md docs/ README.md CHANGELOG.md shmup_plan.md shmup_progress.md` and replace each with a backticked name.
- **[convention]** Finishing a step also means the **"As built"** bullet list under the step in `shmup_plan.md` (what was done, what was deliberately *not* done and why, every budget that moved and its arithmetic) and flipping the resume header of `shmup_progress.md` (the done count, the done list, "Next steps", the "`master` = …" line). Grep the old step id there before committing.
- **[pattern]** When an implementation or a figure's *definition* changes, sweep for the wording as well as the numbers before committing: `grep -rn "<phrase>" --include=*.md --include=*.mjs --include=*.ts docs tools packages test apps`. A single M3-02e budget change touched `shmup_feat.md`, two e2e docblocks, `rendering-and-shell.md`, `api-reference.md`, `render-performance-review.md` and `input-probe-results.md`. Nothing in `pnpm test` checks that the prose agrees with the code — but `test/integration/e2e-docs.test.ts`, `release-audit.test.ts`, `module-layout.test.ts` and `render-telemetry-pipeline.test.ts` do check parts of it, so run those four (≈ 13 s) after a docs sweep.
- **[pattern]** To run `pnpm bench` on an idle box without babysitting it, chain the wait and the run in **one backgrounded** Bash call: `for i in $(seq 1 60); do L=$(cut -d' ' -f1 /proc/loadavg); if [ "${L%%.*}" -lt 6 ]; then break; fi; sleep 20; done; uptime; pnpm bench > $SCR/bench.txt 2>&1; echo "exit=$?"; grep -a "\[bench\] render" $SCR/bench.txt`. Then poll the task's `.output` for the literal `exit=` marker (`grep -q "exit="`), not for non-emptiness — the early `uptime` line makes `[ -s … ]` true long before the bench has run.
- **[gotcha]** A browser spec that counts *per-frame* events (`structureRebuilds` over 180 rAF frames) measures the **machine**, not the code: the same assertion that read 18/300 on an idle box read 88/180 inside a full `pnpm test:e2e`, failing a `< FRAMES / 8` gate. Do not tighten or loosen such a threshold — record the figure with `testInfo.annotations.push({ type, description })` and gate instead on the *mechanism* (flip the feature on at runtime and assert the counter returns to its quiet value), plus a sanity ceiling like "never more than one per frame".
- **[convention]** When a measured figure turns out to be machine-dependent, the doc that tells the owner to read it on the TV must say so too — `docs/dev/rendering-and-shell.md`'s `REB` row now says "read the rate, not the total, and read it against the panel", with both the idle and loaded percentages and the condition that zeroes them. A doc that states a bare target for a figure the reader cannot reproduce is a bug report waiting to happen.
- **[pattern]** A source-scanning test (walk `git ls-files <dir>` and assert no file matches a regex) passes vacuously if a path is mistyped or a glob stops matching. Always add the counter-assertions: `expect(listed.length, dir).toBeGreaterThan(0)` per directory and a floor on the total scanned (`expect(scanned).toBeGreaterThan(40)`).
- **[convention]** Finishing a step also means the **"As built"** bullet list under the step in `shmup_plan.md` (what was done, what was deliberately *not* done and why, every budget that moved and its arithmetic) and flipping the resume header of `shmup_progress.md` (the "Done: N of 45 steps" count, the done list, "Next steps", the "`master` = …" line and the batch's step list), plus the row for the step itself. Grep the old step id there before committing.
- **[gotcha]** `pnpm test:e2e -- mode7.spec.ts raster.spec.ts` does **not** filter — it rebuilds both hosts and runs all 267 specs (~3 min). Only `pnpm exec playwright test --config test/e2e/playwright.config.ts --project=chromium <fragment>` filters (~11 s a spec). Use the filtered form to iterate, then one full `pnpm test:e2e` to confirm — a spec that passes filtered can still fail in the full run (the load differs).
- **[pattern]** Rewriting a large block of a TS/spec file from a `python3 - <<'PY'` heredoc: slice with `s.index("  test('<exact first line>")` … `s.rindex("});\n")` rather than matching the whole old body, then pipe the file through `pnpm exec prettier --write <file>` before running it — the hand-written replacement will not match the repo's 100-column style otherwise, and `pnpm format:check` is part of the gate.

- **[pattern]** When a change's headline benefit is a *ratio* (render p95 with a feature vs without), build the A/B into the bench itself — a creation option that restores the old behaviour (`createPixiRenderer({ renderGroups: false })`) plus a scenario that runs the same load both ways in one session. Comparing p95 across separate runs on a shared machine is noise. Quote the ratio as a **range over every run you have** (M3-02e's went 0.92–0.94× in the step's three runs, 0.85× in the docs run, 0.65× in the review's — a 0.65–0.94× spread). If your own verification run lands outside the quoted range, **widen the range and record the spread in every file** (`grep -rn "0.92" --include=*.md .`) rather than swapping in your single new number.
- **[gotcha]** A `python3 - <<'PY' … PY` edit whose `assert old in s` fails returns an **empty tool result** — no traceback, no exit code, nothing. Read `{}` as "the anchor did not match", not as success. Two causes, in order of likelihood: the anchor spans a line break that is not where you think, or the heredoc terminator was not alone on its line (`PY; tail -5 log` silently breaks the whole command — put the follow-up on the next line). Recover by probing first (`print(o in s)` per candidate line), then anchoring on **one line** and asserting `s.count(o) == 1`; confirm exact bytes with `sed -n 'N,Mp' file | cat -A` (em-dashes and arrows show as `M-bM-^FM-^R`). This applies to TS docblocks exactly as it does to Markdown paragraphs.
