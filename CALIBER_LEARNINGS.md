# Caliber Learnings

Accumulated patterns and anti-patterns from development sessions.
Auto-managed by [caliber](https://github.com/caliber-ai-org/ai-setup) — do not edit manually.

- **[convention]** A plan step's outcome is recorded as an `- **As built:**` block appended directly after that step's `- **Refs:**` line in `shmup_plan.md`, with one nested bullet per area (profiles, loop, shell option, tests…), and it explicitly records what was *left out* and why, plus anything still manual (hardware / account checks). Later review fixes get their own nested bullet under that list (e.g. `- **Review fixes (round 1).** …`), naming the symptom, the call site that was missing, and whether any golden hash moved — do not rewrite the original "As built" prose.
- **[fix]** Wrapping a wait in a *background Bash* task (`until grep -q EXIT= log; do sleep 5; done`) does not help — that task's own output file is also empty until it exits, so you end up polling the poller. Go straight to `Monitor` with `tail -f -n 0 "$LOG" | grep -E --line-buffered "<done marker>|✘|failed|Error:"` and a generous `timeout_ms`, and redirect the real command's output to a log file you can `tail` directly meanwhile.
- **[gotcha]** Vitest's asymmetric matchers fail this repo's type-aware lint in tests: `expect(issues).toEqual([expect.objectContaining({ path: expect.stringContaining('x'), … })])` trips `@typescript-eslint/no-unsafe-assignment`. Write the assertion positionally instead — `expect(issues).toHaveLength(1); expect(issues[0].message).toBe(…)` — or compare against a plain `[{ path, message }]` literal.
- **[gotcha]** SoA pool field names come from the `*_SCHEMA` constant, not from the system's prose — `bullets.points.fields` has `player` (the credited slot), not `owner`, and a wrong name reads back `undefined`. Grep the `..._SCHEMA = Object.freeze({` block in the module before naming a field in a test.
- **[pattern]** Edit long prose lines in Markdown/README/plan files with a `python3 - <<'PY'` heredoc that asserts the old substring exists before replacing (`assert old in s; s = s.replace(old, new, 1)`) — the anchors in these docs are 100-column wrapped sentences that are hard to match exactly with Edit, and the `assert` turns a silent no-op into a visible failure. Follow the edit with `npx prettier --write <files>` (Markdown at the repo root *is* Prettier-checked by `pnpm format:check`, even though `docs/` tables are hand-kept).
- **[pattern]** After adding a doc page, verify its cross-links mechanically rather than by eye: a short `python3` pass over `\]\(([^)#\s]+)(#[^)]*)?\)` in the new/edited files, resolving each relative target with `os.path.normpath` and checking existence, plus a second pass comparing `#anchor` fragments against the target file's GitHub-slugged `#` headings. Nothing in `pnpm test` checks doc links generally.
- **[gotcha]** `pnpm test`'s unfiltered tail is only Vitest's per-project "Transform |<project>| transforming modules took Ns" advisory — `tail -25` shows six of those and **no** pass/fail line, which reads as a silent failure. Always `grep -E "Test Files|Tests |FAIL"` instead (current baseline: 652 files / 7839 tests). Same for `pnpm build` → `grep -E "Tizen bundle OK|Tasks:|ERROR"`.
- **[pattern]** The whole gate does fit in one Bash call when you pass an explicit long `timeout` (e.g. 1_800_000) and tail/grep each stage: `pnpm format:check 2>&1 | tail -5 && pnpm lint 2>&1 | tail -5 && pnpm typecheck 2>&1 | tail -5 && pnpm test 2>&1 | grep -E "Test Files|Tests " && pnpm build 2>&1 | tail -20` — ≈ 4–5 min (lint ≈ 75 s uncached, typecheck ≈ 26 s, build ≈ 18 s, test ≈ 70 s, e2e ≈ 3.5 min for 259 specs). Without an explicit timeout the chain dies at the 120 s default and only the first command's output survives.
- **[pattern]** Re-check the Tizen size budgets without a rebuild: `node apps/tizen/scripts/check-bundle.mjs` (runs fine from the repo root, no `cd`) reads the existing `apps/tizen/dist/` and prints `Tizen bundle OK: app.js … KB (… gzip of 512.0 KB) … N files in dist/`. Run it straight after a root `pnpm build` instead of paying for `pnpm --filter @shmup/tizen build` again.
- **[gotcha]** A lookup table written as a plain `Object.freeze({ … })` record still answers to `constructor`, `toString`, `valueOf` and friends, and this repo's id patterns (e.g. `INPUT_PROFILE_ID_PATTERN = /^[a-z0-9]+(?:-[a-z0-9]+)*$/`) **accept** `constructor` — so an unguarded `TABLE[id]` on a user-supplied id returns a function. Guard every variable-key lookup of an object-literal table with `Object.prototype.hasOwnProperty.call(TABLE, key)` (`Object.hasOwn` is banned for Chromium 69) and type-check the result. Audit new code for this with `git show <ref> -- 'packages/*/src/*' 'apps/*/src/*' | grep -E '^\+' | grep -E '\[[a-z][A-Za-z0-9_.]*\]'`.
- **[pattern]** When adding a regression test for a prototype-pollution-style hole, assert both halves: that the pattern-*accepted* keys (`constructor`, `valueof`, `tostring`) come back unchanged as strings, and that the pattern-*rejected* ones (`__proto__`, `toString`, `hasOwnProperty`) still resolve to `null` — the latter proves the validation, not the guard, is what rejects them.
- **[convention]** A regression test's reason is recorded twice: in the test file's top docblock (`Regression: <old behaviour> (now <new>)`, appended after any existing regression note) and as a comment inside the `it(...)` naming the exact mechanism. Existing edge files such as `packages/core/test/config/config-user-options-edge.test.ts` already follow this — extend the docblock's summary sentence rather than replacing it.
- **[pattern]** Edit long prose lines in Markdown/README/plan *and* TypeScript files with a `python3 - <<'PY'` heredoc that asserts the old substring exists before replacing (`assert old in s` / `assert s.count(anchor)==1`) — the anchors are 100-column wrapped sentences that are hard to match exactly with Edit, and the assert turns a silent no-op into a visible failure. Follow Markdown edits with `npx prettier --write <files>` (root Markdown *is* Prettier-checked by `pnpm format:check`).

Later review fixes get their own nested bullet (e.g. `- **Review fixes (round 1).** …`) naming the symptom and the call site — do not rewrite the original "As built" prose.
- **[pattern]** A background research/review Agent's full report lives in its raw task output file (`/tmp/claude-*/…/tasks/<task-id>.output`, JSONL of message events), not just in the notification excerpt. Extract the last assistant `text` block with a small `python3` pass over the lines (`json.loads(ln)['message']['content']`) and write it to a scratchpad `.md` before the notification text scrolls away.
- **[gotcha]** `pnpm install --frozen-lockfile` is near-instant here (~30 ms, "resolution step is skipped") — running it before a gate costs nothing and rules out a stale link, so keep it at the head of the verification chain.
- **[pattern]** `pnpm vitest run <single test path>` works from the repo root against the multi-project config (≈ 0.4 s for one core file) — use it for the tight edit/test loop and save `pnpm test` for the final gate.
- **[gotcha]** `pnpm lint` only prints `Failed: <task>` at the tail — the actual ESLint messages are swallowed by Turborepo's summary. Re-run just the failing task to see them: `pnpm lint:root 2>&1 | tail -30` for `//#lint:root`, `pnpm --filter @shmup/core lint 2>&1 | tail -20` for a package. To find which file is at fault in a long `unbound-method` dump, `pnpm --filter <pkg> lint 2>&1 | grep -E "^/home|\.ts$" | head -5`.
- **[gotcha]** Test *helpers* are linted with the same type-aware rules as sources. Two traps that bite repeatedly: a harness object literal whose shorthand method is later destructured trips `@typescript-eslint/unbound-method` — declare it as a property with an arrow (`readonly more: (d: readonly number[]) => number[]` / `more: (deltas) => {…}`) instead of `more(deltas) {…}`; and a ternary used as a statement (`cond ? a.push(x) : a.push(y)`) trips `@typescript-eslint/no-unused-expressions` — write `a.push(cond ? x : y)`.
- **[pattern]** For a long run whose result you need in full, redirect to a log file in the session scratchpad and background the Bash call (`pnpm test > …/scratchpad/full-test.log 2>&1; echo "exit=$?"; grep -aE "Test Files|Tests  " …`) — then pull the failure detail out of the log with `grep -a -A30 "Failed Tests" <log>`. The `-a` matters: Vitest's log has escape bytes and plain `grep` calls it a binary file.
- **[gotcha]** `apps/electron`'s `test/main/main.test.ts` (the F11 fullscreen / Ctrl+= scale `vi.waitFor` assertion) is flaky under the full `pnpm test` load — it passes on its own (`pnpm --filter @shmup/electron exec vitest run test/main/main.test.ts`, ~2 s) and on a second full run. Before chasing it, re-run the single file, then re-run `pnpm test`; only treat it as a real break if it fails twice.
- **[pattern]** `pnpm format:check && pnpm lint && pnpm typecheck` chained in one Bash call exceeds the 120 s foreground timeout unless you pass an explicit long `timeout` (e.g. 900000–1800000) and tail/grep each stage. Rough budget: `pnpm format:check` ≈ 30 s, `pnpm lint` ≈ 75 s uncached, `pnpm typecheck` ≈ 25 s, `pnpm build` ≈ 47 s (9 turbo tasks), `pnpm test` ≈ 76 s (659 files / 7958 tests), `pnpm test:e2e` ≈ 3.5 min (259 specs).
- **[gotcha]** Do not poll a background Bash task by `until [ -s <its .output file> ]` from *another* background task — the poller's own output file is also empty until it exits, so you end up polling the poller. Either poll from a foreground call with a long `timeout`, or wait on the real process (`until ! ps aux | grep -q "[v]itest run --project integration"; do sleep 5; done`), or use `Monitor` with `tail -f` on a log you redirected yourself.
- **[pattern]** A lint rule that only covers part of the tree needs a belt-and-braces source scan test beside it: `apps/web/src` switches `no-restricted-syntax` off wholesale (it may use `import.meta`), so a banned pattern there passes lint. `test/integration/eslint-rules.test.ts` pairs each fixture-snippet rule check with a `readdirSync` walk over every runtime `src/` tree asserting the offender list is empty.
