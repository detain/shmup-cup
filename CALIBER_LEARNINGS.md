# Caliber Learnings

Accumulated patterns and anti-patterns from development sessions.
Auto-managed by [caliber](https://github.com/caliber-ai-org/ai-setup) — do not edit manually.

- **[convention]** A new browser-side benchmark or harness under `test/bench/` is **not** part of `pnpm test` (its own Vitest config) — but it still needs `test/tsconfig.json` updated to cover the new files, or `pnpm typecheck` skips them silently. Pair it with a headless `test/integration/*.test.ts` that reads the bench sources as text and asserts the claims only a browser run could otherwise verify — that pulls the bench's invariants into `pnpm test` without launching a browser.
- **[gotcha]** `pnpm test:e2e` under load can fail two `determinism.spec.ts` cases with `Test timeout of 60000ms exceeded while setting up "page"` — a machine-contention symptom, not a determinism regression. Confirm by re-running just that spec (`pnpm exec playwright test --config test/e2e/playwright.config.ts --project=chromium determinism`, ~11 s for 73 tests) and then the full suite on a quiet machine; do not start debugging hashes off the first failure.
- **[convention]** Test counts quoted in `shmup_progress.md` must come from the run that actually passed — an interrupted or contended `pnpm test:e2e` prints a smaller total (`260 passed` + 2 failed vs the true `262 passed`). Re-read the number from the green run before writing the row.
- **[convention]** When a bench figure and an on-device figure differ because the bench deliberately runs a harsher load (its particle pool is 512 vs the shipped 256), say so where both are printed — otherwise the next reader "reconciles" them as a bug.
- **[pattern]** When a measured number changes, sweep for **every** place it was written down before committing: `grep -rn "<the figure>" --include=*.md --include=*.ts . | grep -v node_modules`. One bench figure lived in the plan's As-built block, two `docs/dev/*.md` files (one a results table header) and a module docblock; nothing in `pnpm test` checks that they agree.
- **[convention]** A plan step's outcome is recorded as an `- **As built:**` block appended directly after that step's `- **Refs:**` line in `shmup_plan.md`, with one nested bullet per area. Beyond "what was left out and why" and "still manual", the strongest blocks also record **where the implementation deviated from the plan's wording and why** and **how a measured number must not be over-read** (e.g. "these milliseconds are SwiftShader's and do not predict the Mali-G51"). Review fixes get their own nested bullet (`(review round 1)`) — do not rewrite the original prose.
- **[fix]** `@typescript-eslint/unbound-method` also fires when you *read or reassign a class's method as a value* — hooking a third-party singleton (`const original = TexturePool.createTexture; pool.createTexture = wrapper`) errors in both the source and the test's fake. The fix that works here: declare a local `interface` whose member is a **property with a function type**, cast the class through it, and build the fake from that interface with an arrow property.
- **[gotcha]** Do not poll a background Bash task by `until [ -s <its .output file> ]` from *another* background task — the poller's own output file is also empty until it exits, so you end up polling the poller. A backgrounded `pnpm …` task's `.output` file can stay **0 bytes for its whole run** (the harness only flushes when the pipeline ends). Redirect yourself instead: `(pnpm test:e2e > $SCR/e2e.log 2>&1; echo "exit=$?" >> $SCR/e2e.log)` in the background, then poll with `until grep -q "exit=" $SCR/e2e.log; do sleep 15; done` from the foreground with a long `timeout`.
- **[gotcha]** A `for i in $(seq …); do … sleep 20; done` wait loop is itself foregrounded and will hit the 600 s tool timeout and get backgrounded, leaving a stray poller process. Prefer one foreground call with an explicit long `timeout` and a `grep`-on-sentinel loop, and remember the finished background task's `.output` *is* readable once `[exited with code N]` appears in it.
- **[pattern]** The whole gate fits in a few Bash calls if you pass an explicit long `timeout` (900000–1800000) and tail/grep each stage. Current budget: `pnpm format:check` ≈ 30 s, `pnpm lint` ≈ 30–85 s (uncached ≈ 1 m 21 s, 9 turbo tasks), `pnpm typecheck` ≈ 17–31 s, `pnpm test` ≈ 75 s–10 min under load, `pnpm build` ≈ 19–47 s, `pnpm test:e2e` ≈ 4 min (262 specs), `pnpm bench` ≈ 3 min (the render bench alone ≈ 2 min). Without an explicit timeout the chain dies at the 120 s default and only the first command's output survives.
- **[gotcha]** `pnpm test`'s unfiltered tail is only Vitest's per-project "Transform |<project>| transforming modules took Ns" advisory — `tail -25` shows six of those and **no** pass/fail line, which reads as a silent failure. Always `grep -E "Test Files|Tests |FAIL"` instead (current baseline: 668 files / 8,021 tests). Same for `pnpm build` → `grep -iE "app.js|gzip|Tizen bundle OK|ERROR"` (current: `app.js 1500.5 KB (386.8 KB gzip of 512.0 KB), 5 files in dist/ (1638.9 KB of 8192.0 KB)`), and for `pnpm bench` → `grep -E "Test Files|Tests |FAIL|Duration"` plus `grep -E "^\[bench\]"` for the per-scenario lines.
- **[pattern]** The whole gate fits in a few Bash calls if you pass an explicit long `timeout` (900000–1800000) and tail/grep each stage. Current budget: `pnpm install --frozen-lockfile` ~35 ms, `pnpm format:check` ≈ 30 s, `pnpm lint` ≈ 30–85 s (cached/uncached), `pnpm typecheck` ≈ 17–31 s, `pnpm test` ≈ 75 s–10 min under load, `pnpm build` ≈ 5–47 s, `pnpm test:e2e` ≈ 2.7–4 min (262 specs), `pnpm bench` ≈ 3 min (the render bench alone ≈ 2 min). Without an explicit timeout the chain dies at the 120 s default and only the first command's output survives.
- **[fix]** When a chained `pnpm format && pnpm lint && pnpm typecheck && pnpm test` call hits the 120 s tool timeout and returns *empty* stdout, do not re-run the chain — the harness backgrounds it and keeps going. `cat` the returned `backgroundTaskId`'s `.output` file (`…/tasks/<id>.output`) instead; once `[exited with code N]` is in it, every stage's grep output is there.
- **[gotcha]** Do not poll a background Bash task by `until [ -s <its .output file> ]` from *another* background task — the poller's own output file is also empty until it exits, so you end up polling the poller. A backgrounded `pnpm …` task's `.output` can stay 0 bytes for its whole run. Redirect yourself instead: `(pnpm test:e2e > $SCR/e2e.log 2>&1; echo "EXIT=$?" >> $SCR/e2e.log)` in the background, then poll from the foreground with `timeout 110 bash -c 'until grep -q "EXIT=" $SCR/e2e.log; do sleep 10; done'` — the sentinel is both the completion marker and the status. Keep the inner `timeout` under the 120 s tool limit so the poll returns instead of being backgrounded.
- **[pattern]** Edit long prose lines in Markdown/plan *and* TypeScript files with a `python3 - <<'PY'` heredoc that asserts the old substring exists before replacing (`assert old in s`, or a `rep(a, b)` helper that asserts then `replace(a, b, 1)`) — the anchors are 100-column wrapped sentences that are hard to match exactly with Edit, and the assert turns a silent no-op into a visible failure. Chain `pnpm format` (or `npx tsc --noEmit -p <pkg>/tsconfig.json`, or a focused `npx vitest run --root <pkg> test/<module>`) in the *same* Bash call so a broken edit is caught immediately.
- **[pattern]** One python heredoc can carry an `edits = [(path, old, new), …]` list across `shmup_plan.md`, `CHANGELOG.md` and `shmup_progress.md` at once, each with its own `assert a in s, (p, a[:60])`. That is the cheapest way to keep the three plan-driven records in step in a single commit.
- **[fix]** Do not chain `git fetch && git rebase origin/master && git add …` before staging — the rebase aborts on a dirty working tree (`error: cannot rebase: You have unstaged changes`) and the whole chain returns with nothing done. Stage first (`git add <explicit paths>`), or compare `git log --oneline origin/master -1` against `git log --oneline -1` and skip the rebase when the remote has not moved.
- **[pattern]** Before hooking or measuring a Pixi internal, read the installed source rather than guessing: `sed -n '1,90p' node_modules/.pnpm/pixi.js@<version>/node_modules/pixi.js/lib/rendering/renderers/shared/texture/TexturePool.mjs`. That is how the power-of-two rounding of `getOptimalTexture` and the `_texturePool` free-list shape were confirmed — the published typings do not show either.
- **[gotcha]** A Node-side unit-test fake of a Pixi global only covers the *creation* path. `test/e2e/render-profile.spec.ts` is what catches a counter that reads 0 in a real browser because the state existed before the counter started — when a debug figure is asserted in e2e, expect that spec to fail first and treat the Node tests as insufficient proof on their own.
- **[convention]** A new shipped code path that reuses an existing shader/program must be added to the e2e compile check (`test/e2e/mode7.spec.ts` compiles every vertex/fragment pairing in a real WebGL1 context) *alongside* the old pairing, not in place of it — the escape-hatch path still ships and still has to link on Chromium 69.

- **[pattern]** When a code change makes a helper accept new state, widen the test's fake factory with an *optional* parameter (`fakePool(free?)`) and add the `@param` line to its docblock in the same edit — jsdoc lint fails the run otherwise, and the existing zero-argument call sites keep working unchanged.
