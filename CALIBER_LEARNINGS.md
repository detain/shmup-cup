# Caliber Learnings

Accumulated patterns and anti-patterns from development sessions.
Auto-managed by [caliber](https://github.com/caliber-ai-org/ai-setup) — do not edit manually.

- **[gotcha]** Under heavy load (`uptime` 45–68, ~50 vitest forks) `pnpm test` reports `[vitest-pool]: Timeout terminating forks worker` and `test/scripts/audio-preview.test.ts` fails at its 60 s limit, and `pnpm test:e2e` can fail `determinism.spec.ts` with `Test timeout of 60000ms exceeded while setting up "page"`. Re-run the single file/spec before treating either as a regression, and never start `pnpm test`, `pnpm test:e2e` and `pnpm bench` concurrently — they starve each other.
- **[gotcha]** `test/bench/zones.perf.ts` "zone I" is the canary of the bench suite: its median sits right at the 1 ms/tick budget and it fails when `pnpm bench` shares the machine. **Always run `pnpm bench` alone on an idle machine**; re-run it alone before treating a zone tick-budget failure as a regression.
- **[gotcha]** `pgrep -fc playwright` counts browser helper processes, not remaining tests — it swings 40→80→40 while a run is healthy, and a directory of `test-results/` entries is not a failure count (Playwright makes a folder per *attempt*). The only trustworthy signal is the run's own final `N passed (Xm)` line.
- **[fix]** Do NOT quote a hand-computed gzip of the Tizen bundle. `node -e "gzipSync(readFileSync('apps/tizen/dist/app.js'))"` printed **397.4 KB** while the build printed `Tizen bundle OK: app.js 1500.5 KB (386.8 KB gzip of 512.0 KB)` — `check-bundle.mjs` measures the budgeted payload. The figure for `CHANGELOG.md` / `shmup_progress.md` is the one from the `Tizen bundle OK:` line of a fresh build.
- **[fix]** `git rebase` aborts with `error: cannot rebase: You have unstaged changes` when the step's work is not yet staged — and chaining `git rebase … && git add …` in one command cannot help, because the rebase runs first and the rest of the `&&` chain is lost. Check first: when `git log --oneline origin/master -1` equals `git log --oneline -1` there is nothing to rebase — just `git add` the step's files. Otherwise use `git rebase --autostash origin/master`.
- **[pattern]** Write the commit message to a scratchpad file first (`$SCR/commit-msg.txt`, then `git commit -F`) — these messages are multi-paragraph prose naming each new test file, the bug each suite caught, and how a measured number must not be over-read; composing them inline loses the formatting and cannot be revised.
- **[convention]** Finishing a step also means flipping the resume header of `shmup_progress.md` (the "Done: N of 45 steps" count, the list of done steps, the "Next steps" sentence, the "`master` = …" line and the batch's step list), plus the row for the step itself. Grep the old step id there before committing — the header lists pending steps by name.
- **[pattern]** When an implementation or a figure's *definition* changes, sweep for the wording as well as the numbers before committing: `grep -rn "<phrase>" --include=*.md --include=*.mjs --include=*.ts docs tools packages test apps`. One M3-02f wording fix touched six files plus a test. Nothing in `pnpm test` checks that the prose agrees with the code — but `test/integration/e2e-docs.test.ts`, `release-audit.test.ts`, `module-layout.test.ts` and `render-telemetry-pipeline.test.ts` do check parts of it, so run those four (≈ 13 s) after a docs sweep.
- **[pattern]** Verify a statistics change by re-implementing it standalone in a throwaway `node` script under the scratchpad and comparing against the exact answer over synthetic data, rather than trusting the unit tests: a unit test proves the code does what it does; this proves the *quantity* is the one claimed.
- **[convention]** Never claim an on-device millisecond figure is "comparable" with a `pnpm bench` figure. The bench runs Chromium + SwiftShader on a shared desktop; only its **counted** quantities (draw calls, pooled render-target bytes, structure rebuilds, heap delta) and its **in-run ratios** transfer to the TV. The correct wording when two figures share a definition is "the same **statistic**, not a comparable **magnitude**" — say which, in every place the number is described, and compare milliseconds only with other milliseconds measured on the same monitor.
- **[pattern]** Count a step's new test cases from the diff rather than by hand: `git diff <first-sha>~1 <last-sha> -- '*test*' '*spec*' | grep -c "^+.*\b\(it\|test\)\(\.each\)\?("` (and the `^-` variant for removals) — the number goes into the progress row beside the suite totals.
- **[convention]** Never claim an on-device millisecond figure is "comparable" with a `pnpm bench` figure. The bench runs Chromium + SwiftShader on a shared desktop; only its **counted** quantities (draw calls, pooled render-target bytes, scene/group rebuilds, heap delta) and its **in-run ratios** transfer to the TV. The correct wording when two figures share a definition is "the same **statistic**, not a comparable **magnitude**" — say which, in every place the number is described, and compare milliseconds only with other milliseconds measured on the same monitor.
- **[pattern]** When a change's headline benefit is a *ratio* (render p95 with a feature vs without), build the A/B into the bench itself — a creation option that restores the old behaviour (`createPixiRenderer({ renderGroups: false })`) plus a scenario that runs the same load both ways in one session. Comparing p95 across separate runs on a shared machine is noise; comparing within one run is the only honest form. Then quote the ratio as a **range over ≥ 3 runs** ("0.92–0.94×"), never the single number the first run printed.
- **[pattern]** A counter that goes down after an optimization needs a companion counter proving the work did not just move out of sight (`structureRebuilds` → 0 is only credible beside `groupRebuilds` ≈ 1,590). Add the second figure to the bench result type and to the same log line; keep it **off** the on-device debug overlay so the owner still reads one number on the TV.
- **[pattern]** To calibrate a budget constant (`DRAW_CALL_BUDGET`, size caps) to what the code actually does, temporarily set it to an impossible value (`= 1`), run the specs, and read the real figures out of `Expected: <= 1 / Received: 7` in the failure output — faster and more exact than instrumenting the page. Then write the new value **with its arithmetic in the docblock** and sweep the same number into `shmup_feat.md` §22 and `docs/dev/rendering-and-shell.md`.
- **[pattern]** Before an experiment that edits shipped source just to measure it (trying 6 vs 9 vs 11 render-group layers), copy the file into the scratchpad first (`cp packages/.../index.ts $SCR/layers-11.ts`) and `cp` it back when done — the python-anchored edits used for these experiments are not reversible by re-running them.
- **[gotcha]** `pnpm test:e2e -- mode7.spec.ts raster.spec.ts` does **not** filter — it rebuilds both hosts and runs all 267 specs (~3 min). Only `pnpm exec playwright test --config test/e2e/playwright.config.ts --project=chromium <fragment>` filters (~11 s a spec).
- **[gotcha]** ESLint runs type-aware over `test/` too (`eslint --max-warnings=0 .`), so a Pixi mock written with a hand-rolled structural `interface Group` plus `as unknown as Group` fails `@typescript-eslint/no-unnecessary-type-assertion`. Type mock helpers with the library's own types (`Pixi.RenderGroup`) and drop the cast — `pnpm typecheck` alone will not catch this.
- **[gotcha]** When a test asserts the *presence* of a bug ("`structureRebuilds` keeps rising every frame"), fixing the bug fails that test legitimately. Rewrite it to assert the fix **and** keep the original guarantee it was standing in for (the counter is still read in the right place — Pixi clears `structureDidChange` while rendering, so a misplaced read sits at 0 for ever), and say in the plan's "As built" that the test changed meaning.
- **[fix]** When such an `assert old in s` fails on a Markdown paragraph, the anchor almost always spans a line break that is not where you think. Shorten the anchor to **one line** and confirm the exact bytes first with `sed -n 'N,Mp' file | cat -A` (em-dashes and arrows show as `M-bM-^FM-^R`), rather than guessing at the wrap.
- **[gotcha]** Vitest does not type-check, so a test fixture that goes stale when you add a **required** field to an exported type still passes `pnpm test` and fails only `pnpm typecheck` (`error TS2741: Property 'hist' is missing …`). After widening a shared type (e.g. a new field on `RenderBenchResult`), run `pnpm typecheck` and fix every fixture literal before believing a green focused test run.
- **[convention]** Test counts quoted in `shmup_progress.md` must come from the run that actually passed — write the row with a placeholder and fill it from the green run; a guess is always wrong. Current baselines (2026-09-16, M3-02e): root suite **679 files / 8,143 tests**, e2e **267 specs** (chromium + the Firefox determinism spec), `pnpm bench` render scenarios all green, shell project 63 files / 457 tests, `tools/input-probe` **20 files / 533 tests**.
- **[fix]** `vitest run --project test …` fails with `No projects were found. The filter matched no projects: test` even though `vitest.config.ts` lists `'test'` in `projects` — that entry is a *directory*, and its project **name** comes from `defineShmupProject()` (it is `integration`). Either filter by the real name (`--project integration`) or just pass file paths.
- **[gotcha]** A bare `npx vitest run <paths>` from the root silently **drops paths that belong to another project** — passing three files reported `Test Files 2 passed (2)` with no warning. Always check the file count in the summary equals the number of files you named; run package files with `pnpm --filter @shmup/<pkg> exec vitest run test/<path>` instead.
- **[pattern]** Focused runs: a whole package project is `pnpm vitest run --project render-pixi` (≈ 14 s, 67 files); a single new suite is `pnpm vitest run --project <name> -t "<describe fragment>"` (prints `2 passed | 67 skipped`). The render bench alone is `pnpm exec vitest run --config test/bench/vitest.config.ts render.perf` (~2–3 min, so background it) and `-t "worst-case, CRT off"` narrows it to the two A/B scenarios (~30 s).
- **[pattern]** The whole gate fits in a few Bash calls if you pass an explicit long `timeout` (900000–1800000) and grep each stage; without one the chain dies at the 120 s default and only the first command's output survives. Current budget: `pnpm format:check` ≈ 30 s, `pnpm lint` ≈ 24–78 s, `pnpm typecheck` ≈ 29–35 s, `pnpm test` ≈ 100 s–10 min under load, `pnpm build` ≈ 5–47 s, `pnpm test:e2e` ≈ 3 min, `pnpm bench` ≈ 3–5 min. Greps that show a result: `pnpm build` → `grep -iE "app.js|gzip|Tizen bundle OK|ERROR"`; `pnpm test:e2e` → `grep -iE "passed|failed|flaky"`; `pnpm bench` → `grep -E "^\[bench\]"`.
- **[pattern]** Long-running verification runs in one backgrounded shell that writes its own log and a done-marker, then block in a background Bash call with `until [ -f $SCR/phase2.done ]; do sleep 5; done; grep …`. A backgrounded task's own `.output` file stays **0 bytes until it exits**, so never poll *that*; and a `cat`/`tail` of a not-yet-created log makes the Bash call fail with empty output — guard with `2>/dev/null` or wait on the marker.
- **[convention]** TSDoc `{@link X}` must never survive into a `.md` file — it renders literally. After copying docblock prose into docs, run `grep -rn "{@link" --include=*.md docs/ README.md CHANGELOG.md shmup_plan.md shmup_progress.md` and replace each with a backticked name.
- **[convention]** Finishing a step also means the **"As built"** bullet list under the step in `shmup_plan.md` (what was done, what was deliberately *not* done and why, every budget that moved and its arithmetic) and flipping the resume header of `shmup_progress.md` (the done count, the done list, "Next steps", the "`master` = …" line). Grep the old step id there before committing.
- **[pattern]** When an implementation or a figure's *definition* changes, sweep for the wording as well as the numbers before committing: `grep -rn "<phrase>" --include=*.md --include=*.mjs --include=*.ts docs tools packages test apps`.
