# Caliber Learnings

Accumulated patterns and anti-patterns from development sessions.
Auto-managed by [caliber](https://github.com/caliber-ai-org/ai-setup) — do not edit manually.

- **[convention]** Test counts quoted in `shmup_progress.md` must come from the run that actually passed — write the row with a placeholder and fill it from the green run. A guess is always wrong: "33 new (8,316 in the suite)" was really 39 new / 8,050, and an earlier row guessed "16 new (8,027)" for 10 new / 8,021. Current baseline: **671 files / 8,050 tests**, 266 e2e specs.
- **[pattern]** When an implementation changes, sweep the prose for **both the numbers and the mechanism name** before committing: `grep -rn "<figure>" --include=*.md .` and `grep -rn "<old mechanism>" --include=*.md docs *.md packages/*/README.md`. Renaming a Pixi filter into a mesh left filter-era wording in six files (two dev guides, a debug-overlay row, a gotcha list, a package README and a module docblock); nothing in `pnpm test` checks that the docs agree with the code.
- **[pattern]** Edit the long-prose docs with a python heredoc that asserts the old text first (`assert old in s; s = s.replace(old, new)`) rather than a blind `sed`. The assert is what catches an upstream rewrite or an already-applied edit, and it is the same technique that resolves rebase conflicts in these files.
- **[convention]** A rebase rewrites the commit SHA, so write the `shmup_progress.md` step row with a literal `COMMIT_SHA` placeholder and fill it from `git log --oneline -1` in a follow-up `(+ this row fix)` edit.
- **[convention]** A plan step's outcome is recorded as an `- **As built:**` block appended directly after that step's `- **Refs:**` line in `shmup_plan.md`, one nested bullet per area, each bullet's bold lead sentence naming the trap and then which test caught it. The same finding is mirrored into `CHANGELOG.md` and `shmup_progress.md` in the same commit. Beyond "what was left out and why" and "still manual", the strongest blocks record **where the implementation deviated from the plan's wording and why** and **how a measured number must not be over-read**. Review fixes get their own nested bullet (`(review round 1)`) — do not rewrite the original prose.
- **[pattern]** The whole gate fits in a few Bash calls if you pass an explicit long `timeout` (900000–1800000) and grep each stage. Current budget: `pnpm format:check` ≈ 30 s, `pnpm lint` ≈ 30–88 s (9 turbo tasks, uncached), `pnpm typecheck` ≈ 17–35 s, `pnpm test` ≈ 75 s–10 min under load, `pnpm build` ≈ 5–47 s, `pnpm test:e2e` ≈ 2.7–4 min (266 specs), `pnpm bench` ≈ 3 min. Greps that actually show a result: `pnpm test` → `grep -E "Test Files|Tests |FAIL"`; `pnpm build` → `grep -iE "app.js|gzip|Tizen bundle OK|ERROR"` (current: `app.js 1500.5 KB (386.8 KB gzip of 512.0 KB)`); `pnpm test:e2e` → `grep -iE "passed|failed|flaky"`; `pnpm bench` → `grep -E "^\[bench\]"`. Without an explicit timeout the chain dies at the 120 s default and only the first command's output survives.
- **[gotcha]** Do not poll a background Bash task by `until [ -s <its .output file> ]` from *another* background task — the poller's own output file is also empty until it exits, and a backgrounded `pnpm …` task's `.output` can stay **0 bytes for its whole run**. Redirect yourself instead: `(pnpm test:e2e > $SCR/e2e.log 2>&1; echo "EXIT=$?" >> $SCR/e2e.log)` in the background, then poll from the foreground with `timeout 110 bash -c 'until grep -q "EXIT=" $SCR/e2e.log; do sleep 10; done'`. Never fill the wait with `echo ok` no-op calls.
- **[gotcha]** `pnpm test:e2e` under load can fail two `determinism.spec.ts` cases with `Test timeout of 60000ms exceeded while setting up "page"` — machine contention, not a determinism regression. Confirm by re-running just that spec (`pnpm exec playwright test --config test/e2e/playwright.config.ts --project=chromium determinism`, ~11 s), then the full suite on a quiet machine; do not start debugging hashes off the first failure.
- **[gotcha]** Under heavy load (`uptime` load average ~45, ~50 vitest forks) `pnpm test` reports `[vitest-pool]: Timeout terminating forks worker` and `test/scripts/audio-preview.test.ts` fails at its 60 s limit; the same file passes in ~13 s alone. Re-run the individual file before treating it as a regression, and do not start `pnpm test`, `pnpm test:e2e` and `pnpm bench` concurrently — they starve each other.
- **[pattern]** Validate every new pixel/shader e2e assertion by mutation: `cp <file> $SCR/<file>.bak`, splice a one-line break with a python heredoc that `assert`s the old text is present, `build:test`, re-run only that spec, then restore from the backup and rebuild. A break that fails exactly one new test and nothing else is the evidence the assertion is worth committing, and the commit message records it.
- **[fix]** `git rebase` aborts with `error: cannot rebase: Your index contains uncommitted changes` / `You have unstaged changes` when the step's work is still staged or unstaged — a `git stash push -- <one file>` does not clear the rest of the index. Commit first, then `git fetch && git rebase origin/master`; skip the rebase entirely when `git log --oneline origin/master -1` equals `git log --oneline -1`.
- **[gotcha]** Prettier's `format:check` covers the docs even though the repo excludes Markdown *formatting* rules in places — run `pnpm format:check` after a batch of python-heredoc doc edits; a spliced paragraph that exceeds the 100-column convention is the usual cause of a late failure.
- **[fix]** Do NOT quote a hand-computed gzip of the Tizen bundle. `node -e "gzipSync(readFileSync('apps/tizen/dist/app.js'))"` printed **397.4 KB** while `pnpm --filter @shmup/tizen build` printed `Tizen bundle OK: app.js 1500.5 KB (386.8 KB gzip of 512.0 KB)` for the same step — `check-bundle.mjs` measures the budgeted payload, the raw file is larger. The budget figure that goes into `CHANGELOG.md` / `shmup_progress.md` is the one from the `Tizen bundle OK:` line of a fresh `pnpm --filter @shmup/tizen build`; a root `pnpm build` alone leaves `apps/tizen/dist/` in a state whose raw gzip does not match it.
- **[env]** `tools/input-probe/` is outside the pnpm workspace and uses **npm**: the root gate does not cover it. After touching anything under it, run `cd tools/input-probe && npm run verify` (vite build → `check-compat.mjs`: `app.js` parses as an ES2018 classic script, `index.html` has no module tag, `config.xml` + `icon.png` present) and `npm test` there — `pnpm test` will not.
- **[pattern]** To get a build-time value (an env var such as `VITE_REPORT_URL`) into shipped/dev code, add a **define** in `shmupBuildInfo()` (`vite.shared.ts`) plus a declaration in `types/build-info.d.ts` — `apps/*/src` may not use `import.meta` (Chromium 69 / the classic IIFE bundle). Fill the define only in dev / test builds and leave it `''` in release so the minifier drops the feature, and assert its absence from the release `dist/app.js` in `apps/tizen/test/build/tizen-build.test.ts`. Touching `types/**` re-runs typecheck everywhere (`turbo.json` `globalDependencies`).
- **[fix]** New source and test files written during a step routinely fail `pnpm format:check` (Prettier reflows long signatures and `Object.freeze([...])` calls). Fix them with `npx prettier --write <the exact files>` and re-run `pnpm format:check` rather than `pnpm format`, which rewrites the whole tree and can drag unrelated files into the commit.
- **[pattern]** A focused Playwright run is `timeout 600 pnpm exec playwright test --config test/e2e/playwright.config.ts --project=chromium <file-fragment>` (≈ 11 s for one spec) — far faster than `pnpm test:e2e`, which rebuilds both hosts and runs ~266 specs in 3–4 min.
- **[pattern]** A focused package run is `npx vitest run --root packages/<pkg> test/<module>` (≈ 3–6 s, and its summary line prints reliably); `pnpm --filter @shmup/<pkg> exec vitest run test/<path>` works the same way for a single file.
- **[gotcha]** A piped `pnpm test 2>&1 | tail -N` is unreliable: sometimes it shows `Test Files` / `Tests`, sometimes the pipe drops them and leaves only Vitest's transform advisories plus `[ELIFECYCLE] Test failed` while the harness records `[exited with code 0]`. A *finished background* task's `.output` can be just as empty. Redirect instead — `pnpm test > $SCR/test.txt 2>&1; echo "exit=$?"; grep -nE "FAIL|Tests  |Test Files|AssertionError" $SCR/test.txt` — and never conclude the suite failed from an empty grep.

- **[gotcha]** In render-pixi tests, Pixi v8 types `Container.children` as `Container[]` (so `child as Container` trips `@typescript-eslint/no-unnecessary-type-assertion` in `pnpm lint`) while `view.parent` is `Container | null` (so it needs `as Pixi.Container` or `tsc` fails with TS18047). Lint and typecheck bite from opposite directions — run both after touching a test that walks the scene graph.
- **[pattern]** Before hooking or measuring a Pixi internal, read the installed source rather than guessing: `sed -n '1,90p' node_modules/.pnpm/pixi.js@<version>/node_modules/pixi.js/lib/rendering/renderers/shared/texture/TexturePool.mjs`. That is how `getOptimalTexture`'s power-of-two rounding and the `_texturePool` free-list shape were confirmed — the published typings show neither.
- **[pattern]** When teardown is the thing under test, remember `bindWorld(null)` only *hides* an effect pass's nodes — meshes, geometry/shader/GlProgram and second-pass containers are the pass's own and must be destroyed explicitly in `PixiRenderer.destroy()`. Any new pass needs its own line there plus a regression test that fails without it.
