# Caliber Learnings

Accumulated patterns and anti-patterns from development sessions.
Auto-managed by [caliber](https://github.com/caliber-ai-org/ai-setup) — do not edit manually.

- **[gotcha]** A browser spec that counts *per-frame* events (`structureRebuilds` over 180 rAF frames) measures the **machine**, not the code: the same assertion that read 18/300 on an idle box read 88/180 inside a full `pnpm test:e2e`, failing a `< FRAMES / 8` gate. Do not tighten or loosen such a threshold — record the figure with `testInfo.annotations.push({ type, description })` and gate instead on the *mechanism* (flip the feature on at runtime and assert the counter returns to its quiet value), plus a sanity ceiling like "never more than one per frame".
- **[convention]** When a measured figure turns out to be machine-dependent, the doc that tells the owner to read it on the TV must say so too — `docs/dev/rendering-and-shell.md`'s `REB` row now says "read the rate, not the total, and read it against the panel", with both the idle and loaded percentages and the condition that zeroes them. A doc that states a bare target for a figure the reader cannot reproduce is a bug report waiting to happen.
- **[pattern]** A source-scanning test (walk `git ls-files <dir>` and assert no file matches a regex) passes vacuously if a path is mistyped or a glob stops matching. Always add the counter-assertions: `expect(listed.length, dir).toBeGreaterThan(0)` per directory and a floor on the total scanned (`expect(scanned).toBeGreaterThan(40)`).
- **[convention]** Finishing a step also means the **"As built"** bullet list under the step in `shmup_plan.md` (what was done, what was deliberately *not* done and why, every budget that moved and its arithmetic) and flipping the resume header of `shmup_progress.md` (the "Done: N of 45 steps" count, the done list, "Next steps", the "`master` = …" line and the batch's step list), plus the row for the step itself. Grep the old step id there before committing.
- **[gotcha]** `pnpm test:e2e -- mode7.spec.ts raster.spec.ts` does **not** filter — it rebuilds both hosts and runs all 267 specs (~3 min). Only `pnpm exec playwright test --config test/e2e/playwright.config.ts --project=chromium <fragment>` filters (~11 s a spec). Use the filtered form to iterate, then one full `pnpm test:e2e` to confirm — a spec that passes filtered can still fail in the full run (the load differs).
- **[pattern]** Rewriting a large block of a TS/spec file from a `python3 - <<'PY'` heredoc: slice with `s.index("  test('<exact first line>")` … `s.rindex("});\n")` rather than matching the whole old body, then pipe the file through `pnpm exec prettier --write <file>` before running it — the hand-written replacement will not match the repo's 100-column style otherwise, and `pnpm format:check` is part of the gate.
- **[convention]** Test counts quoted in `shmup_progress.md` must come from the run that actually passed — write the row with a placeholder and fill it from the green run; a guess is always wrong. Current baselines (2026-09-16, M3-02e review): root suite **683 files / 8,169 tests**, e2e **277 specs** (chromium + the Firefox determinism spec), `pnpm bench` render scenarios all green, `tools/input-probe` **20 files / 533 tests**.
- **[gotcha]** A bare `npx vitest run <paths>` from the root silently **drops paths that belong to another project** — passing three files reported `Test Files 2 passed (2)` with no warning. Always check the file count in the summary equals the number of files you named; to run files from two projects in one command, name both (`pnpm vitest run --project integration --project render-pixi <paths…>`) and verify the test count.
- **[pattern]** The whole gate fits in a few Bash calls if you pass an explicit long `timeout` (900000–1800000) and grep each stage; without one the chain dies at the 120 s default and only the first command's output survives. Current budget: `pnpm format:check` ≈ 30 s, `pnpm lint` ≈ 24–79 s, `pnpm typecheck` ≈ 29–35 s, `pnpm test` ≈ 84 s–10 min under load, `pnpm build` ≈ 5–47 s, `pnpm test:e2e` ≈ 3 min, `pnpm bench` ≈ 3–5 min. Greps that show a result: `pnpm build` → `grep -iE "app.js|gzip|Tizen bundle OK|ERROR"`; `pnpm test:e2e` → `grep -iE "passed|failed|flaky"`; `pnpm bench` → `grep -E "^\[bench\]"`.
- **[pattern]** When a change's headline benefit is a *ratio* (render p95 with a feature vs without), build the A/B into the bench itself — a creation option that restores the old behaviour (`createPixiRenderer({ renderGroups: false })`) plus a scenario that runs the same load both ways in one session. Comparing p95 across separate runs on a shared machine is noise. Quote the ratio as a **range over every run you have** (M3-02e's went 0.92–0.94× in the step's three runs, 0.85× in the docs run, 0.65× in the review's — a 0.65–0.94× spread). If your own verification run lands outside the quoted range, **widen the range and record the spread in every file** (`grep -rn "0.92" --include=*.md .`) rather than swapping in your single new number.
- **[gotcha]** A `python3 - <<'PY' … PY` edit whose `assert old in s` fails returns an **empty tool result** — no traceback, no exit code, nothing. Read `{}` as "the anchor did not match", not as success. Two causes, in order of likelihood: the anchor spans a line break that is not where you think, or the heredoc terminator was not alone on its line (`PY; tail -5 log` silently breaks the whole command — put the follow-up on the next line). Recover by probing first (`print(o in s)` per candidate line), then anchoring on **one line** and asserting `s.count(o) == 1`; confirm exact bytes with `sed -n 'N,Mp' file | cat -A` (em-dashes and arrows show as `M-bM-^FM-^R`). This applies to TS docblocks exactly as it does to Markdown paragraphs.
- **[gotcha]** In-document anchors are not checked by anything in `pnpm test` — a plausible-looking `#the-render-profile-reb-and-rt` pointed at no heading. Before writing a `[text](#anchor)` into a doc, list the real headings with `grep -n "^#" <file>` and derive the slug from one of them.

- **[convention]** The Tizen bundle figure quoted in `CHANGELOG.md` / `shmup_progress.md` comes from the build's own line, never an estimate: `pnpm build 2>&1 | grep "Tizen bundle OK"` → `app.js 1500.9 KB (386.9 KB gzip of 512.0 KB)`. Re-run the build after the last edit and quote that run.

- **[pattern]** Docblock-only edits are not free: they change a package's lint / typecheck inputs, so after a late round of prose edits inside `packages/*/src` re-run the gate rather than trusting the earlier green. With turbo's cache it costs ~30 s lint + ~19 s typecheck (8 of 9 packages cached).
- **[convention]** Test counts quoted in `shmup_progress.md` must come from the run that actually passed — write the row with a placeholder and fill it from the green run; a guess is always wrong. Current baselines (2026-09-16, after M3-03): root suite **695 files / 8,269 tests**, e2e **277 specs** (chromium + the Firefox determinism spec), bench 21 tests, `tools/input-probe` **20 files / 533 tests**.
- **[gotcha]** `pnpm format` / `pnpm format:check` / `pnpm lint` chained in one foreground Bash call routinely exceeds the 120 s default and the call returns **empty output with a `backgroundTaskId`** — the work is still running, not failed. Read the task's `.output` file afterwards rather than re-running the chain.
- **[pattern]** Long-running verification runs in one backgrounded shell that writes its own log and a done-marker, then block in a background Bash call with `until [ -f $SCR/phase2.done ]; do sleep 5; done; grep …`. A backgrounded task's own `.output` file stays **0 bytes until it exits**, so never poll *that* for size — block on a string the run prints at the end instead (`until grep -qE "Test Files" …/<id>.output; do sleep 5; done`), which works because the harness flushes the file progressively for piped output. A `cat`/`tail` of a not-yet-created log makes the Bash call fail with empty output — guard with `2>/dev/null` or wait on the marker.
- **[pattern]** Adding a host app means sweeping the host lists in the docs, not just adding a page: the ASCII host box and the "new host platform" extension row in `docs/dev/architecture.md`, the build-outputs and root-scripts tables in `docs/dev/build-test-deploy.md`, the profile / per-host tables in `docs/dev/input-profiles.md`, plus `repo-layout.md` and the root README. `grep -n "apps/tizen\b" docs/dev/*.md` finds most of them; a bare `grep -n "<newhost>"` returning nothing across those files means the sweep has not been done.
- **[pattern]** A brand-new test file is fastest written with `cat > path <<'TSEOF' … TSEOF` in the same Bash call that runs its suite (`… && pnpm --filter @shmup/<pkg> test 2>&1 | grep -E "× |Tests |AssertionError" -A 10 | head -30`). Model a new app's build-output test on `apps/tizen/test/build/tizen-build.test.ts` — read it first: the pattern is `vi.stubEnv('NODE_ENV', 'production')` around a programmatic `build()` from `vite` into an `mkdtempSync` dir, a 120 s `beforeAll` timeout, and `rmSync` in `afterAll`.
- **[convention]** The Tizen / webOS bundle figures quoted in `CHANGELOG.md` / `shmup_progress.md` come from the build's own line, never an estimate: `pnpm build 2>&1 | grep "bundle OK"` → `app.js 1532.1 KB (395.5 KB gzip of 512.0 KB)`. Re-run the build after the last edit and quote that run.
- **[gotcha]** When one app reads a file out of another app's folder (webOS reusing `apps/tizen/polyfills/` and `apps/tizen/scripts/check-bundle.mjs`), add those paths to `turbo.json`'s `globalDependencies` — Turborepo's per-package input hashing does not see across package boundaries, so the borrowing app's build cache would stay valid after the shared file changed. Say so in the borrowing config's docblock too.
- **[fix]** `git rebase origin/master` aborts with `error: cannot rebase: You have unstaged changes.` on a large in-progress step. Check `git log --oneline -1 origin/master` against `HEAD` first — when origin has not moved there is nothing to rebase, so skip it and go straight to the scoped `git add`.
- **[pattern]** Stage a big step with one explicit `git add <paths…>` list (new directories like `apps/webos` can be named whole) and then verify before committing: `git status --porcelain | grep -v "^A \|^M " | head` must print nothing, and `git status --porcelain | awk '{print $1}' | sort | uniq -c` plus `git diff --cached --stat | tail -3` shows the added/modified counts. Never `git add -A` — the working tree carries untracked junk.
- **[gotcha]** `git status --porcelain` shows a brand-new directory as one line (`apps/webos/`); to see and count its files use `git status --porcelain --untracked-files=all <dir>`.
