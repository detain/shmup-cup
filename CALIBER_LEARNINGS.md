# Caliber Learnings

Accumulated patterns and anti-patterns from development sessions.
Auto-managed by [caliber](https://github.com/caliber-ai-org/ai-setup) — do not edit manually.

- **[convention]** Never claim an on-device millisecond figure is "comparable" with a `pnpm bench` figure. The bench runs Chromium + SwiftShader on a shared desktop; only its **counted** quantities (draw calls, pooled render-target bytes, structure rebuilds, heap delta) and its **in-run ratios** transfer to the TV. The correct wording when two figures share a definition is "the same **statistic**, not a comparable **magnitude**" — say which, in every place the number is described.
- **[convention]** A per-frame/per-tick path stays measured, not asserted: when a fix adds work to a sampler, put the fold on the cold path (`close()` / the report timer) and prove `commitFrame`-style hot functions are **byte-for-byte unchanged** (`git show <sha> -- <file>`) plus run the guard alone (`pnpm --filter @shmup/shell exec vitest run test/telemetry/telemetry-alloc.test.ts`). Grep every `.close(` / `.report()` call site to confirm the cold path is the only caller. A cheap way to pin "the measurement did not move onto the frame" is a spy over `%TypedArray%.prototype.sort` / `Array.prototype.sort` asserting zero calls across 1000 frames and exactly N per closed window.
- **[gotcha]** Vitest does not type-check, so a test fixture that goes stale when you add a **required** field to an exported type still passes `pnpm test` and fails only `pnpm typecheck` (`error TS2741: Property 'hist' is missing …`). After widening a shared type in `packages/*/src`, run `pnpm typecheck` before believing a green focused test run.
- **[gotcha]** Under heavy load (`uptime` 45–68, ~50 vitest forks) `pnpm test` reports `[vitest-pool]: Timeout terminating forks worker` and `test/scripts/audio-preview.test.ts` fails at its 60 s limit, and `pnpm test:e2e` can fail `determinism.spec.ts` cases with `Test timeout of 60000ms exceeded while setting up "page"`. Re-run the single file/spec before treating either as a regression, and never start `pnpm test`, `pnpm test:e2e` and `pnpm bench` concurrently — they starve each other.
- **[pattern]** A focused Playwright run is `timeout 600 pnpm exec playwright test --config test/e2e/playwright.config.ts --project=chromium <file-fragment>` (≈ 11 s for one spec) — far faster than `pnpm test:e2e`, which rebuilds both hosts and runs 267 specs in ~3.5 min.
- **[convention]** A receiver/formatter that prints untrusted JSON must route every interpolated nested value through a total `str()` helper — `{"toString": 1}` is valid JSON with no primitive form and throws inside a template literal, and a `verdicts` / `env` that is not an object throws on property access. The handler's `catch` keeps the process alive but silently loses the line the owner watches while capturing; a seeded-junk fuzz suite (`tools/input-probe/test/logServerFuzz.test.ts`) is what catches it.
- **[convention]** Test counts quoted in `shmup_progress.md` must come from the run that actually passed — write the row with a placeholder and fill it from the green run; a guess is always wrong. Current baselines (2026-09-16, M3-02f): root suite **677 files / 8,137 tests**, e2e **267 specs** (chromium + the Firefox determinism spec), `pnpm bench` 4 files / 19 tests, shell project 63 files / 457 tests, `tools/input-probe` **20 files / 533 tests**.
- **[gotcha]** `tools/*` is outside the pnpm workspace, so `pnpm test` never runs the input probe's suite. Verify it separately from `tools/input-probe`: `npm test` (20 files / 533 tests) or `npm run verify` (build + tests + `check:compat`, which asserts `app.js` still parses as an ES2018 classic script). Any edit to `tools/input-probe/server/log-server.mjs` needs that run before committing.
- **[fix]** `vitest run --project test …` fails with `No projects were found. The filter matched no projects: test` even though `vitest.config.ts` lists `'test'` in `projects` — that entry is a *directory*, and its project **name** comes from `defineShmupProject()` (it is `integration`). Either filter by the real name (`--project integration`) or just pass file paths: `npx vitest run test/integration/a.test.ts test/integration/b.test.ts` runs them from the root with no filter at all.
- **[gotcha]** A bare `npx vitest run <paths>` from the root silently **drops paths that belong to another project** — passing three files (two in `test/integration`, one in `packages/shell/test`) reported `Test Files 2 passed (2)` with no warning. Always check the file count in the summary equals the number of files you named; run package files with `pnpm --filter @shmup/<pkg> exec vitest run test/<path>` instead.
- **[gotcha]** Vitest's final summary is written near the **top** of a redirected log (around line 6), not at the end — `tail` of `pnpm test > log` shows only the transform/`fsModuleCache` advisories and proves nothing. Always `grep -E "Test Files|Tests |FAIL" <log>`; the same applies to `tools/input-probe`'s `npm test`.
- **[pattern]** The whole gate fits in a few Bash calls if you pass an explicit long `timeout` (900000–1800000) and grep each stage; without one the chain dies at the 120 s default and only the first command's output survives. Current budget: `pnpm format:check` ≈ 30 s, `pnpm lint` ≈ 21–88 s, `pnpm typecheck` ≈ 17–35 s, `pnpm test` ≈ 100 s–10 min under load, `pnpm build` ≈ 5–47 s, `pnpm test:e2e` ≈ 3.5 min, `pnpm bench` ≈ 3–5 min. Greps that show a result: `pnpm build` → `grep -iE "app.js|gzip|Tizen bundle OK|ERROR"`; `pnpm test:e2e` → `grep -iE "passed|failed|flaky"`; `pnpm bench` → `grep -E "^\[bench\]"`.
- **[pattern]** Long-running verification runs in one backgrounded shell that writes its own log and a done-marker: `(pnpm test:e2e >$SCR/e2e.log 2>&1; cd tools/input-probe && npm run verify >$SCR/probe.log 2>&1; echo DONE >$SCR/phase2.done) &`, then block in a background Bash call with `until [ -f $SCR/phase2.done ]; do sleep 5; done; grep …`. A backgrounded task's own `.output` file stays **0 bytes until it exits**, so never poll *that*; and a `cat`/`tail` of a not-yet-created log makes the Bash call fail with empty output — guard with `2>/dev/null` or wait on the marker.
- **[pattern]** Edit the huge single-line rows of `shmup_progress.md` (7,000–8,000 characters each) and long doc paragraphs with an anchored `python3 - <<'PY'` script that does `assert old in s; s = s.replace(old, new, 1)` — the assert turns a stale anchor into a loud failure instead of a silent no-op, and heredocs survive the em-dashes, backticks and `§` the prose is full of. Inspect such a row with `awk '/^\| M3-02f/{print length($0)}'` / `tail -c 2500`, never by reading the whole file.
- **[convention]** TSDoc `{@link X}` must never survive into a `.md` file — it renders literally. After copying docblock prose into docs, run `grep -rn "{@link" --include=*.md docs/ README.md CHANGELOG.md shmup_plan.md shmup_progress.md` and replace each with a backticked name (plus the value, e.g. `` `RENDER_REPORT_INTERVAL_MS` (3 s)``).
- **[convention]** A new build define (`__SHMUP_REPORT_URL__` joining `__SHMUP_DEV__` / `__SHMUP_BUILD__`) has a fixed documentation footprint: `types/build-info.d.ts`, `vite.shared.ts`'s `shmupBuildInfo()`, the defines table **and** the "Two/Three Vite defines decide" sentence in `docs/dev/debug-and-replays.md`, both apps' `main.ts` snippets in that file, `docs/dev/README.md`, the package README and `docs/dev/api-reference.md`. Grep the old define names to find every spot before claiming the docs are updated.
- **[pattern]** A focused Vitest run from the repo root is `pnpm vitest run --project <shell|core|integration|…> 2>&1 | grep -E "Test Files|Tests |FAIL"`; a focused package run is `npx vitest run --root packages/<pkg> test/<module>` or `pnpm --filter @shmup/<pkg> exec vitest run test/<path>` (≈ 4 s for a single allocation guard). Keep `pnpm test` for the gate.
- **[pattern]** Prettier's own binary checks a subset far faster than the turbo task: `npx prettier --check <the files you touched>` (seconds) before the full `pnpm format:check`. Markdown *is* checked by Prettier here despite the hand-made tables, so a rewritten doc paragraph can fail it.
- **[env]** `test/e2e/playwright.config.ts` sets `retries: ci ? 1 : 0` — a local `pnpm test:e2e` has **zero retries**, so a single load-induced flake fails the whole run. Re-run the one spec before calling it a regression.
- **[gotcha]** Under heavy load (`uptime` 45–68, ~50 vitest forks) `pnpm test` reports `[vitest-pool]: Timeout terminating forks worker` and `test/scripts/audio-preview.test.ts` fails at its 60 s limit, and `pnpm test:e2e` can fail `determinism.spec.ts` with `Test timeout of 60000ms exceeded while setting up "page"`. Re-run the single file/spec before treating either as a regression, and never start `pnpm test`, `pnpm test:e2e` and `pnpm bench` concurrently — they starve each other.
- **[gotcha]** `test/bench/zones.perf.ts` "zone I" is the canary of the bench suite: its median sits right at the 1 ms/tick budget and it fails when `pnpm bench` shares the machine. **Always run `pnpm bench` alone on an idle machine**; re-run it alone before treating a zone tick-budget failure as a regression.
- **[gotcha]** `pgrep -fc playwright` counts browser helper processes, not remaining tests — it swings 40→80→40 while a run is healthy, and a directory of `test-results/` entries is not a failure count (Playwright makes a folder per *attempt*). The only trustworthy signal is the run's own final `N passed (Xm)` line.
- **[fix]** Do NOT quote a hand-computed gzip of the Tizen bundle. `node -e "gzipSync(readFileSync('apps/tizen/dist/app.js'))"` printed **397.4 KB** while the build printed `Tizen bundle OK: app.js 1500.5 KB (386.8 KB gzip of 512.0 KB)` — `check-bundle.mjs` measures the budgeted payload. The figure for `CHANGELOG.md` / `shmup_progress.md` is the one from the `Tizen bundle OK:` line of a fresh build.
- **[fix]** `git rebase` aborts with `error: cannot rebase: You have unstaged changes` when the step's work is not yet staged — and chaining `git rebase … && git add …` in one command cannot help, because the rebase runs first and the rest of the `&&` chain is lost. Check first: when `git log --oneline origin/master -1` equals `git log --oneline -1` there is nothing to rebase — just `git add` the step's files. Otherwise use `git rebase --autostash origin/master`.
- **[pattern]** Write the commit message to a scratchpad file first (`$SCR/commit-msg.txt`, then `git commit -F`) — these messages are multi-paragraph prose naming each new test file, the bug each suite caught, and how a measured number must not be over-read; composing them inline loses the formatting and cannot be revised.
- **[convention]** Finishing a step also means flipping the resume header of `shmup_progress.md` (the "Done: N of 45 steps" count, the list of done steps, the "Next steps" sentence, the "`master` = …" line and the batch's step list), plus the row for the step itself. Grep the old step id there before committing — the header lists pending steps by name.
- **[pattern]** When an implementation or a figure's *definition* changes, sweep for the wording as well as the numbers before committing: `grep -rn "<phrase>" --include=*.md --include=*.mjs --include=*.ts docs tools packages test apps`. One M3-02f wording fix touched six files plus a test. Nothing in `pnpm test` checks that the prose agrees with the code — but `test/integration/e2e-docs.test.ts`, `release-audit.test.ts`, `module-layout.test.ts` and `render-telemetry-pipeline.test.ts` do check parts of it, so run those four (≈ 13 s) after a docs sweep.
- **[pattern]** Verify a statistics change by re-implementing it standalone in a throwaway `node` script under the scratchpad and comparing against the exact answer over synthetic data, rather than trusting the unit tests: a unit test proves the code does what it does; this proves the *quantity* is the one claimed.
- **[convention]** Never claim an on-device millisecond figure is "comparable" with a `pnpm bench` figure. The bench runs Chromium + SwiftShader on a shared desktop; only its **counted** quantities (draw calls, pooled render-target bytes, structure rebuilds, heap delta) and its **in-run ratios** transfer to the TV. - **[pattern]** Count a step's new test cases from the diff rather than by hand: `git diff <first-sha>~1 <last-sha> -- '*test*' '*spec*' | grep -c "^+.*\b\(it\|test\)\(\.each\)\?("` (and the `^-` variant for removals) — the number goes into the progress row beside the suite totals.
