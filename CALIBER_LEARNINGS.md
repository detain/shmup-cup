# Caliber Learnings

Accumulated patterns and anti-patterns from development sessions.
Auto-managed by [caliber](https://github.com/caliber-ai-org/ai-setup) — do not edit manually.

- **[pattern]** To get a build-time value (an env var such as `VITE_REPORT_URL`) into shipped/dev code, add a **define** in `shmupBuildInfo()` (`vite.shared.ts`) plus a declaration in `types/build-info.d.ts` — `apps/*/src` may not use `import.meta` (Chromium 69 / the classic IIFE bundle). Fill the define only in dev / test builds and leave it `''` in release so the minifier drops the feature, and assert its absence from the release `dist/app.js` in `apps/tizen/test/build/tizen-build.test.ts`. Touching `types/**` re-runs typecheck everywhere (`turbo.json` `globalDependencies`).
- **[fix]** New source and test files written during a step routinely fail `pnpm format:check` (Prettier reflows long signatures and `Object.freeze([...])` calls). Fix them with `npx prettier --write <the exact files>` and re-run `pnpm format:check` rather than `pnpm format`, which rewrites the whole tree and can drag unrelated files into the commit.
- **[pattern]** A focused Playwright run is `timeout 600 pnpm exec playwright test --config test/e2e/playwright.config.ts --project=chromium <file-fragment>` (≈ 11 s for one spec) — far faster than `pnpm test:e2e`, which rebuilds both hosts and runs ~266 specs in 3–4 min.
- **[pattern]** A focused package run is `npx vitest run --root packages/<pkg> test/<module>` (≈ 3–6 s, and its summary line prints reliably); `pnpm --filter @shmup/<pkg> exec vitest run test/<path>` works the same way for a single file.
- **[gotcha]** A piped `pnpm test 2>&1 | tail -N` is unreliable: sometimes it shows `Test Files` / `Tests`, sometimes the pipe drops them and leaves only Vitest's transform advisories plus `[ELIFECYCLE] Test failed` while the harness records `[exited with code 0]`. A *finished background* task's `.output` can be just as empty. Redirect instead — `pnpm test > $SCR/test.txt 2>&1; echo "exit=$?"; grep -nE "FAIL|Tests  |Test Files|AssertionError" $SCR/test.txt` — and never conclude the suite failed from an empty grep.
- **[convention]** Test counts quoted in `shmup_progress.md` must come from the run that actually passed — write the row with a placeholder and fill it from the green run; a guess is always wrong ("33 new (8,316)" was really 39 / 8,050). Current baseline after M3-02f: **674 files / 8,095 tests**, 266 e2e specs.
- **[pattern]** The whole gate fits in a few Bash calls if you pass an explicit long `timeout` (900000–1800000) and grep each stage; without one the chain dies at the 120 s default and only the first command's output survives. Current budget: `pnpm format:check` ≈ 30 s, `pnpm lint` ≈ 30–88 s (9 turbo tasks), `pnpm typecheck` ≈ 17–35 s, `pnpm test` ≈ 100 s–10 min under load, `pnpm build` ≈ 5–47 s, `pnpm test:e2e` ≈ 2.7–4 min, `pnpm bench` ≈ 3 min. Greps that show a result: `pnpm test` → `grep -E "Test Files|Tests |FAIL"`; `pnpm build` → `grep -iE "app.js|gzip|Tizen bundle OK|ERROR"`; `pnpm test:e2e` → `grep -iE "passed|failed|flaky"`; `pnpm bench` → `grep -E "^\[bench\]"`.
- **[gotcha]** Under heavy load (`uptime` ~45, ~50 vitest forks) `pnpm test` reports `[vitest-pool]: Timeout terminating forks worker` and `test/scripts/audio-preview.test.ts` fails at its 60 s limit (~13 s alone), and `pnpm test:e2e` can fail two `determinism.spec.ts` cases with `Test timeout of 60000ms exceeded while setting up "page"`. Re-run the single file/spec before treating either as a regression, and never start `pnpm test`, `pnpm test:e2e` and `pnpm bench` concurrently — they starve each other.
- **[gotcha]** Do not poll a background Bash task by `until [ -s <its .output file> ]` from *another* background task — the poller's own output file is also empty until it exits, and a backgrounded `pnpm …` task's `.output` can stay **0 bytes for its whole run**. Redirect yourself: `(pnpm test:e2e > $SCR/e2e.log 2>&1; echo "EXIT=$?" >> $SCR/e2e.log)` in the background, then poll from the foreground with `timeout 110 bash -c 'until grep -q "EXIT=" $SCR/e2e.log; do sleep 10; done'`. Never fill the wait with `echo ok` no-ops.
- **[gotcha]** In render-pixi tests, Pixi v8 types `Container.children` as `Container[]` (so `child as Container` trips `@typescript-eslint/no-unnecessary-type-assertion` in `pnpm lint`) while `view.parent` is `Container | null` (so it needs `as Pixi.Container` or `tsc` fails with TS18047). Lint and typecheck bite from opposite directions — run both after touching a test that walks the scene graph.
- **[pattern]** Before hooking or measuring a Pixi internal, read the installed source rather than guessing: `sed -n '1,90p' node_modules/.pnpm/pixi.js@<version>/node_modules/pixi.js/lib/rendering/renderers/shared/texture/TexturePool.mjs`. That is how `getOptimalTexture`'s power-of-two rounding and the `_texturePool` free-list shape were confirmed — the published typings show neither.
- **[pattern]** When teardown is the thing under test, remember `bindWorld(null)` only *hides* an effect pass's nodes — meshes, geometry/shader/GlProgram and second-pass containers are the pass's own and must be destroyed explicitly in `PixiRenderer.destroy()`. Any new pass needs its own line there plus a regression test that fails without it.
- **[pattern]** Edit the long-prose docs with a python heredoc that asserts the old text first (`assert old in s; s = s.replace(old, new, 1)`) rather than a blind `sed` — the assert is what catches an upstream rewrite or an already-applied edit, and it is the same technique that resolves rebase conflicts in these files. Find conflict markers with `grep -n "^<<<<<<<\|^=======\|^>>>>>>>" <file>`, keep **upstream's** rewritten section, re-apply your edits onto it, and close with `grep -c "<<<<<<<" <file>` (must print 0) plus `npx prettier --check <file>`.
- **[pattern]** When an implementation changes, sweep the prose for **both the numbers and the mechanism name** before committing: `grep -rn "<figure>" --include=*.md .` and `grep -rn "<old mechanism>" --include=*.md docs *.md packages/*/README.md tools/*/README.md`. Nothing in `pnpm test` checks that the docs agree with the code, and a feature usually touches six or more files (dev guide, client guide, package README, tool README, CHANGELOG, plan).
- **[gotcha]** `pnpm format:check` covers the docs — run it after a batch of python-heredoc doc edits; a spliced paragraph past the 100-column convention is the usual cause of a late failure.
- **[convention]** A plan step's outcome is recorded as an `- **As built:**` block appended directly after that step's `- **Refs:**` line in `shmup_plan.md`, one nested bullet per area, each bullet's bold lead sentence naming the trap and then which test caught it. The same finding is mirrored into `CHANGELOG.md` and `shmup_progress.md` in the same commit. The strongest blocks record **where the implementation deviated from the plan's wording and why** (e.g. "the step's second option was taken") and **how a measured number must not be over-read**. Review fixes get their own nested bullet (`(review round 1)`) — do not rewrite the original prose.
- **[gotcha]** `tools/` is listed in `.prettierignore` ("Standalone tool projects own their formatting"), so `npx prettier --write`/`--check` on a file under `tools/**` silently matches **nothing** — the cheerful `All matched files use Prettier code style!` means zero files were checked, and `--write` leaves the file untouched. Hand-format `tools/input-probe/**` to the same 100-column / single-quote style yourself (ternary arms, wrapped string concatenations); `pnpm format:check` will never catch a lapse there. (Also: the flag is `--log-level`, not `--loglevel`.)
- **[gotcha]** Vitest does not type-check, so a test fixture that goes stale when you add a **required** field to an exported type still passes `pnpm test` and fails only `pnpm typecheck` (`error TS2741: Property 'hist' is missing … but required in type 'RenderSample'`). After widening a shared type in `packages/shell/src` (or any package's public surface), run `pnpm typecheck` before believing a green focused test run — the hand-written sample/fixture factories in `packages/*/test/**` are where it bites.
- **[pattern]** To prove a dev-only feature never reaches a release bundle, run `pnpm build` and then `grep -c "<marker>\|<CONST_NAME>" apps/tizen/dist/app.js apps/web/dist/assets/index-*.js` — both must print 0. The Tizen build test covers `app.js` only; the web bundle needs this manual grep (pick markers that survive minification: string literals and exported constant names, not identifiers).
- **[gotcha]** `test/bench/zones.perf.ts` "zone I" is the canary of the bench suite: its median sits right at the 1 ms/tick budget and it fails (`expected 1.0573936 to be less than 1`) when `pnpm bench` shares the machine with `pnpm test:e2e`. Re-run `pnpm bench` alone before treating it as a regression — the soak, stress and render benches pass either way.
- **[pattern]** A focused Vitest project run from the repo root is `pnpm vitest run --project <shell|core|integration|…> 2>&1 | grep -E "Test Files|Tests |FAIL"` (the shell project: 63 files / 457 tests in a few seconds) — use it between edits and keep `pnpm test` for the gate.
- **[env]** `tools/input-probe/` (npm, outside the pnpm workspace) has its own three-program typecheck: `npm run typecheck` runs `tsconfig.json` + `tsconfig.node.json` + `tsconfig.test.json`. After touching anything there run `npm run typecheck`, `npx vitest run` (18 files / 511 tests) and `npm run verify` (vite build → `check-compat.mjs`) — the root gate covers none of it.

Current baselines: root suite **8,098 tests**, 266 e2e specs, shell project 63 files / 457 tests, `tools/input-probe` 18 files / 511 tests.

- **[fix]** `git rebase` aborts with `error: cannot rebase: You have unstaged changes` when the step's work is not yet staged — and chaining `git rebase … && git add …` in one command cannot help, because the rebase runs first. Commit (or stage and stash) before rebasing; skip the rebase entirely when `git log --oneline origin/master -1` equals `git log --oneline -1`.
- **[fix]** Do NOT quote a hand-computed gzip of the Tizen bundle. `node -e "gzipSync(readFileSync('apps/tizen/dist/app.js'))"` printed **397.4 KB** while `pnpm --filter @shmup/tizen build` printed `Tizen bundle OK: app.js 1500.5 KB (386.8 KB gzip of 512.0 KB)` for the same step — `check-bundle.mjs` measures the budgeted payload, the raw file is larger. The figure that goes into `CHANGELOG.md` / `shmup_progress.md` is the one from the `Tizen bundle OK:` line of a fresh build.
